# 三级分销多品类小程序商城 — 需求文档

版本：V1.2（核心决策已确认）　|　日期：2026-07-29

---

## 1. 项目背景与目标

### 1.1 背景
构建一套面向多品类商品销售的微信小程序商城，引入三级分销体系，激励分销商（团长/推广员）通过社交关系裂变获客。系统包含三端：

| 端 | 使用方 | 载体 |
|---|---|---|
| 消费者商城 | 普通用户 | 微信小程序 |
| 分销商管理端 | 分销商（一/二/三级） | 小程序内独立入口（或 H5） |
| 运营管理后台 | 平台运营方 | Web 管理后台 |

### 1.2 项目目标
- 支持多品类商品的完整电商交易闭环（选品、下单、支付、发货、售后）
- 建立合规的三级分销佣金体系，激励分销商拉新裂变
- 运营方可在 Web 后台完成商品、订单、分销规则、结算、审核等全流程配置与管控
- 架构可扩展，为后续多商户 / 多渠道（视频号、H5）预留空间

### 1.3 已确认前提
- 单商户自营模式（非多商户入驻平台）
- 分销返佣以**实付金额**为计算基数，不含运费
- 微信支付为唯一收单渠道，暂不接入其他支付方式

## 2. 用户角色与权限体系

### 2.1 角色总览

| 角色 | 说明 | 主要使用端 |
|---|---|---|
| 平台超级管理员 | 系统最高权限，账号/权限/全局配置 | Web 后台 |
| 运营人员 | 商品、订单、营销、内容运营 | Web 后台 |
| 财务人员 | 提现审核、对账、发票 | Web 后台 |
| 客服人员 | 售后、工单处理 | Web 后台 |
| 一级分销商（团长） | 直接发展二级分销商 | 小程序分销端 |
| 二级分销商 | 由一级发展，可发展三级 | 小程序分销端 |
| 三级分销商 | 分销体系末端，不可再发展下级 | 小程序分销端 |
| 普通消费者 | 浏览、下单、可申请成为分销商 | 小程序商城端 |

### 2.2 权限设计原则
- Web 后台采用 **RBAC（基于角色的访问控制）**，角色与菜单/按钮级权限解耦，支持自定义角色
- 分销商身份与消费者身份**共存于同一账号**，一个用户可同时是买家和分销商
- 分销关系链一旦建立（A 邀请 B），**默认不可变更**，防止恶意改单薅佣金；如需改绑需走后台人工审核流程

## 3. 系统架构概览

```
                     ┌─────────────────────┐
                     │   微信小程序 - 消费者商城端   │
                     │ 首页/商品/购物车/订单/我的  │
                     └──────────┬──────────┘
                                │
                     ┌──────────▼──────────┐
                     │  微信小程序 - 分销商管理端  │
                     │ 团队/业绩/提现/推广素材   │
                     └──────────┬──────────┘
                                │ API (FastAPI, JWT鉴权)
                     ┌──────────▼──────────┐
                     │       后端服务层        │
                     │ 商品/订单/分销/结算/支付   │
                     │ FastAPI + PostgreSQL   │
                     │ APScheduler(结算/对账)  │
                     └──────────┬──────────┘
                                │
                     ┌──────────▼──────────┐
                     │   Web 运营管理后台 (Vue3) │
                     │ 商品/订单/分销/财务/权限   │
                     └─────────────────────┘
```

技术栈延续现有基础设施惯例：**FastAPI + PostgreSQL（多用户场景从一开始使用 PostgreSQL）+ JWT/RBAC 中间件 + APScheduler + Docker Compose 部署**，Web 端使用 Vue3。可参考 LikeShop 等成熟分销系统的业务模型作为设计校验基准。

## 4. 功能模块设计

### 4.1 消费者小程序商城端

**4.1.1 首页与导航**
- 轮播广告位、多品类分类导航、限时秒杀/拼团入口（可选）、猜你喜欢推荐

**4.1.2 商品模块**
- 多品类商品结构：类目（支持多级）→ 商品 → SKU（多规格，如颜色/尺寸）
- 商品详情：图文详情、规格选择、库存展示、销量、评价
- 商品搜索与筛选（价格区间、销量、分类）

**4.1.3 购物车与下单**
- 购物车增删改、库存校验
- 下单：收货地址管理、运费计算、优惠券/满减、库存锁定
- 微信支付下单与回调处理，支持退款

**4.1.4 订单与售后**
- 订单状态：待付款/待发货/待收货/已完成/已关闭
- 物流查询（对接快递100等物流接口）
- 售后：仅退款、退货退款、换货，支持凭证上传与客服工单流转

**4.1.5 会员与分销入口**
- 会员中心：个人信息、收货地址、优惠券、积分（可选）
- "成为分销商"申请入口，提交后进入**人工审核**流程，审核通过前不显示分销商工作台入口
- 分享商品海报（自动生成带专属推广参数的二维码/海报图）

### 4.2 分销商管理端（小程序内）

**4.2.1 分销商工作台**
- 核心数据看板：今日/本月佣金、团队人数、待结算金额、可提现余额

**4.2.2 团队管理**
- 我的下级列表（二级/三级），支持查看下级业绩（不可查看下下级明细，防止越级信息泄露）
- 团队业绩排行榜（可选，用于激励）

**4.2.3 推广工具**
- 专属推广二维码/小程序码
- 商品推广海报一键生成（商品图 + 二维码 + 分享文案）
- 推广商品列表，含预估佣金展示

**4.2.4 佣金与提现**
- 佣金明细（订单维度：来源订单、层级、金额、状态：待结算/已结算/已失效）
- 提现申请（微信零钱/银行卡），提现记录与状态跟踪
- 佣金规则说明页（供分销商自查）

### 4.3 运营方 Web 管理后台

**4.3.1 商品管理**
- 类目管理（多级类目树）
- 商品管理：新建/编辑/上下架、多规格 SKU 库存管理、批量导入
- 商品分销设置：单品是否参与分销、单品可设置独立佣金比例（设置后覆盖全局默认比例，不设置则沿用全局值）

**4.3.2 订单管理**
- 订单列表、详情、发货（支持批量发货、对接电子面单）
- 售后工单处理、退款审批

**4.3.3 分销体系管理**
- 分销商准入方式：**人工审核邀请制**（用户在小程序发起"成为分销商"申请，需提交必要信息，由运营人员在后台人工审核通过/拒绝后方可获得分销商身份；申请列表支持批量审核、驳回原因填写）
- 分销商列表：层级关系树状展示、状态管理（正常/冻结/清退）
- 佣金比例配置（已确认规则）：后台设置**全局默认比例**（一/二/三级各一个数值，如10%/5%/2%），对全部参与分销的商品生效；商品维度可单独设置比例，一旦设置则**覆盖全局比例**，未设置的商品沿用全局值
- 分销关系人工调整（特殊场景改绑，需操作留痕）

**4.3.4 结算与财务**
- 佣金结算规则配置（如：订单确认收货后 N 天自动解冻结算，售后需扣回已发放佣金）
- 提现审核（人工/自动阈值）
- 财务对账报表（GMV、佣金支出、退款金额）

**4.3.5 营销工具**
- 优惠券、满减满赠活动配置
- 拼团/秒杀活动配置（如需要，M2 阶段评估）

**4.3.6 内容与运营**
- 首页楼层/轮播/专题页可视化配置
- 消息推送（订阅消息模板管理）

**4.3.7 系统管理**
- 账号与角色权限管理（RBAC）
- 操作审计日志（关键操作留痕：佣金规则变更、分销关系改绑、提现审批）
- 系统参数配置

## 5. 三级分销规则设计（核心，需重点评审）

### 5.1 分销关系建立（已确认：终身有效制）
- 消费者通过分销商分享的链接/海报**首次**进入小程序 → 系统自动建立"绑定关系"，**终身有效，不设有效期、不自动解绑**
- 绑定优先级：**首次绑定不可覆盖**（防飞单）——即用户一旦绑定某分销商，后续无论点击其他分销商的推广链接多少次，上级关系均不再变更
- 特殊场景改绑仅能由运营人员在 Web 后台**人工操作**，且需强制填写改绑原因，全程留痕（审计日志），不对用户/分销商开放自助改绑入口

### 5.2 佣金计算模式（已确认：三级分销比例制）

- 计算基数为**实付金额**（不含运费，与优惠/折扣抵扣后的实际支付金额一致）
- 消费者下单 → 其上级（一级）按实付金额 × 一级佣金比例 获得佣金
- 一级的上级（二级）按实付金额 × 二级佣金比例 获得佣金
- 二级的上级（三级）按实付金额 × 三级佣金比例 获得佣金
- 各级比例独立配置，互不冲突，例：一级 10%、二级 5%、三级 2%（具体数值由运营后台配置，非写死）

> **合规提示**：分销层级不超过三级，佣金来源与实际商品购买行为绑定，不采用"仅凭发展下级即可获利"的极差/拉人头模式，本项目已按此原则确定为比例制方案。

### 5.3 佣金结算周期（已确认：确认收货后返佣，退货扣回）
```
下单支付 → 待结算（订单未完成，佣金冻结）
  → 用户确认收货 → 佣金转为"已结算"（可提现）
  → 若已结算后发生退货退款 → 系统自动扣回对应佣金
      → 若佣金尚未提现：直接扣减/作废
      → 若佣金已提现：标记异常，进入财务人工追偿流程（后台留痕）
```
说明：不再额外设置售后期缓冲，以"确认收货"作为结算触发点；需在后台配置**超时自动确认收货天数**（如15天无操作自动确认），避免佣金因用户不确认收货而长期挂起。

### 5.4 特殊规则
- **分销商自购返佣：已确认支持**。分销商本人下单购买，其自身上级（一/二/三级）按正常规则获得佣金；分销商是否可给自己返佣（即自购自返）需在后台单独开关（默认关闭，避免刷单套现风险），仅"自购触发上级返佣"为默认开启项
- 佣金比例采用"全局默认 + 单品覆盖"两级配置：全局设置一/二/三级各一个统一比例数值；单品设置比例后优先按单品比例计算，未设置的商品按全局比例计算（详见 4.3.3）
- 分销商等级晋升规则（如：团队人数满 N 人自动晋升，可选功能，暂不纳入 V1）

## 6. 核心业务流程示例

### 6.1 分销拉新下单流程
```
分销商C分享海报 → 新用户D扫码进入小程序 → 系统记录D的上级为C
→ D浏览下单 → 支付成功 → 系统按分销关系链计算C(一级)/C的上级(二级)/C的上上级(三级)佣金（基数为实付金额）
→ 订单进入"待结算"状态 → D确认收货（或超时自动确认） → 佣金转为"已结算"
→ 分销商在小程序端发起提现 → 运营后台审核 → 财务打款
```

### 6.2 售后退款回滚佣金流程
```
用户申请退款 → 客服/自动审核通过 → 系统检测该订单是否已产生佣金
→ 若佣金状态为"待结算"：直接作废
→ 若佣金状态为"已结算"未提现：扣回
→ 若已提现：标记异常，进入财务人工追偿流程（需在后台留痕）
```

## 7. 核心数据模型（概要）

| 表 | 关键字段 | 说明 |
|---|---|---|
| users | id, openid, phone, parent_distributor_id | 用户主表，含消费者与分销商 |
| distributors | id, user_id, level, status, invite_code | 分销商信息，level=1/2/3 |
| distributor_relations | distributor_id, level1_id, level2_id, level3_id | 冗余存储上三级关系，便于快速查询 |
| products / product_skus | id, category_id, price, stock, commission_rate | 商品与规格 |
| orders / order_items | id, user_id, distributor_chain, amount, status | 订单，记录下单时的分销链快照 |
| commissions | id, order_id, distributor_id, level, amount, status | 佣金明细，status: pending/settled/void |
| withdrawals | id, distributor_id, amount, status, audit_by | 提现记录 |
| commission_rules | scope(global/product), product_id(可空), level(1/2/3), rate | 佣金规则：scope=global 为全局默认规则（每级一条），scope=product 时需关联 product_id，计算时优先取该商品对应 level 的规则，未命中则回退到 global |

> 说明：`distributor_chain` 建议在订单生成时**冗余快照**当时的三级分销关系，避免后续分销关系变更影响历史订单佣金计算。

## 8. 非功能性需求

| 类别 | 要求 |
|---|---|
| 并发与性能 | 商城首页/商品详情接口响应 < 300ms；下单接口需支持库存扣减防超卖（悲观锁/Redis分布式锁） |
| 数据一致性 | 支付回调、库存扣减、佣金计算需保证事务一致性，建议引入消息队列削峰（如订单量大时） |
| 安全合规 | 微信支付签名校验、用户手机号等隐私字段脱敏存储、防刷单/防羊毛党风控规则 |
| 审计 | 分销规则变更、人工改绑、提现审批等关键操作强制记录操作日志 |
| 可扩展性 | 预留多商户、多渠道（视频号小店）扩展接口设计 |
| 部署 | Docker Compose 部署，沿用国内镜像源配置，便于阿里云 ECS 环境快速上线 |

## 11. 决策清单

### 11.1 已确认（本轮评审确定）

| 决策项 | 结论 |
|---|---|
| 商户模式 | 单商户自营 |
| 佣金计算基数 | 实付金额（不含运费） |
| 收单渠道 | 微信支付，唯一渠道 |
| 佣金计算模式 | 三级分销比例制（方案A） |
| 分销商准入方式 | 人工审核邀请制 |
| 佣金结算周期 | 确认收货后返佣，退货扣回 |
| 分销商自购返佣 | 支持（自购触发上级返佣默认开启；自购自返默认关闭，可后台配置） |
| 分销关系绑定规则 | 终身有效，首次绑定不可覆盖，仅运营人工留痕改绑 |
| 佣金比例配置方式 | 全局设置统一比例，单品设置后覆盖全局 |

### 11.2 仍待评审确认

1. **超时自动确认收货天数**：默认设置为多少天（如15天）？
2. **提现审核方式**：是否设置免审核阈值（如≤200元自动打款，超出人工审核）？
3. **全局佣金比例具体数值**：一/二/三级各设为多少（如10%/5%/2%），需运营方结合毛利率给出最终数字
4. **是否需要拼团/秒杀等营销工具**：影响 M2 是否纳入范围
