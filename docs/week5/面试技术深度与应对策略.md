## 一、项目叙事框架（30 秒版 / 2 分钟版 / 5 分钟版）

### 1.1 30 秒电梯演讲

> "我独立完成了一个面向制造业排程排产的多 Agent 系统。它用 LangGraph 做编排、STS Token Exchange 做鉴权、OpenTelemetry 做全链路追踪。支持单 Agent 和多 Agent 两种模式，有完备的 RBAC 权限控制、审计日志、两级缓存、成本监控和预算熔断。代码工程化分层——编排/权限/观测三层对应行业 Harness 架构，从手写 ReAct 原语一路演进到 Supervisor 多 Agent 协作。"

### 1.2 2 分钟架构概述

```
1. 问题背景（30s）
   — 制造业排程排产：订单/库存/设备/客户数据分散，排产员每天要查 5 个系统
   — 目标：用自然语言一句话得到排产建议

2. 技术选型（30s）
   — 编排：LangGraph StateGraph（4 节点 + 条件边 + checkpointer 持久化）
   — 工具：ToolRegistry 注册中心（O(1) 查找 + 参数白名单 + RBAC 集成）
   — 鉴权：STS Token Exchange（RFC 8693）+ RBAC 5 角色 + 洋葱三层防御
   — 观测：OTel 同构自研 Tracer + 可插拔导出（console/otel/OTLP Jaeger）
   — 缓存：L1 精确缓存（SQLite, <1ms）+ L2 语义缓存（Chroma cosine, ~50ms）
   — RAG：BM25 + 向量 + RRF + Cross-Encoder 四步混合检索

3. 架构设计（30s）
   — Harness 三层：编排层（graph/ + agents/）→ 权限层（auth/）→ 观测层（observability/）
   — 双运行模式：单 Agent（LangGraph 状态图）/ 多 Agent（Supervisor + 双子 Agent）
   — 部署：CLI → FastAPI 网关 → Docker 容器化

4. 成果与收获（30s）
   — 从零到接近生产级，7 周 35 天系统训练
   — 代码 37 个 Python 文件，7000+ 行，完整的工程化结构
   — 最大的收获不是"调通了一个框架"，而是理解了 Agent 系统的全链路工程化
```

### 1.3 5 分钟深度讲述

按"演进路线"讲（面试官最爱听"从简单到复杂"的思维过程）：

| 阶段 | 做了什么 | 学到什么 |
|------|---------|---------|
| Week 1-2 | 手写 ReAct 循环、主备 fallback、混合检索 RAG | Agent 原语不是黑盒——三段式（调LLM→判断→执行回传）是所有框架的底座 |
| Week 3 | LangGraph 替代手写循环、MCP 协议化工具 | 框架替你做了状态管理，但手写一遍才知道它藏了什么 |
| Week 4 | Supervisor 多 Agent + Token Exchange + RBAC + 审计 | Agent 安全是全新课题——权限收缩链、不可否认审计、洋葱型防御 |
| Week 5 | OTel 全链路追踪、两级缓存、容器化、成本熔断 | 观测 + 评测 = 持续迭代。没有观测的 Agent 是黑箱中的黑箱 |

## 二、面试官可能深挖的技术点 — 逐题预演

### 2.1 架构设计类

#### Q1："为什么选 LangGraph 而不是自己写循环？"

**面试官在考察**：框架选型能力、对编排的理解深度。

**回答策略**：

> 我一开始是手写 while 循环的（Week 1-2），三个原因最终切到 LangGraph：
>
> 1. **状态管理**：手写循环时状态靠全局变量传，多轮对话、工具结果、迭代计数器散落各处。LangGraph 的 StateGraph 把状态声明为 TypedDict，节点是纯函数（state → state），可测试、可组合。
> 2. **条件路由**：手写循环靠 if/elif 判断"继续调工具还是回答"，条件一多就失控。LangGraph 的 `add_conditional_edges` 把路由逻辑从业务逻辑中解耦。
> 3. **持久化**：LangGraph 的 checkpointer 机制一行代码（`compile(checkpointer=...)`) 就实现多轮对话和重启恢复。手写要做到同样效果，需要自己序列化/反序列化整个状态机。
>
> 但我也保留了手写版的代码（`scripts/week1/day2_function_calling.py`），这样我能讲清楚 LangGraph 替我做了什么、藏了什么——而不是"调通了一个框架"。

**加分点**：提到 StateGraph 的局限演进——`evaluate_results` 最初是 noop，条件边基于消息类型判断（tool → 继续；assistant → 回答）。**R3 已补（2026-08-07）**：`evaluate_results` 现在做真实校验，按工具结果质量标记 `needs_retry`（重试失败的调用）/ `needs_more`（补充更多数据）/ `ready_for_answer`（足够出答案），条件边据此继续循环。但复杂场景仍可再深——显式按每种工具定义"结果质量规则"（如"query_orders 必须返回至少 1 条"），当前是通用规则而非逐工具定制。

---

#### Q2："单 Agent 和多 Agent 的边界在哪里？什么场景该切多 Agent？"

**面试官在考察**：架构决策能力、不滥用模式。

**回答策略**：

> 我的判断标准是**职责分离度**：
>
> - **单 Agent 够用**：所有工具在同一个决策域（如"查订单+查库存+给建议"，目标是同一个——排产决策）
> - **该切多 Agent**：职责天然分离，需要不同视角、不同权限（如"审核订单风险"和"评估产能可行性"是两个独立决策域，前者看客户信用和合同条款，后者看设备和材料）
>
> 具体到代码：
> - 单 Agent 模式：`select_and_execute` 节点一个 LLM 调用决定调哪些工具，Prompt 覆盖所有 7 个工具
> - 多 Agent 模式：Supervisor 不做具体业务（不调工具），只做路由→分发→汇总。审核 Agent 只持 reviewer 令牌（只能看订单/客户），生产 Agent 只持 scheduler 令牌（能看库存/设备）
>
> **反模式警示**：不能为了多 Agent 而多 Agent。如果两个子 Agent 的结果高度耦合（审核结果直接影响排产决策），拆开后协调成本可能超过收益。当前 demo 的审核和生产是松耦合的——审核说"高风险"、生产说"能做"，Supervisor 综合判断——这才值得拆。

**加分点**：举一个不该拆的例子——"如果把查订单和查库存拆成两个 Agent，它们之间的协调开销（两次 LLM 调用 + 路由）远大于一个 Agent 同时查两个工具的延迟"。

---

#### Q3："你的 Token Exchange 和 OAuth2 的 Token Exchange 是什么关系？"

**面试官在考察**：安全基础知识的深度、是否真理解 RFC。

**回答策略**：

> 我的实现遵循 RFC 8693（OAuth 2.0 Token Exchange）的核心语义：
>
> 1. **subject_token → exchanged token**：用户登录后的高权限 Token 作为 subject_token，STS 验证后签发受限的 exchanged token
> 2. **权限收缩（scope down）**：子 Token 的权限必须是父 Token 的子集。我的代码里 `exchange()` 方法逐条校验 `requested_permissions ⊆ parent_permissions`
> 3. **短时效**：子 Token 5 分钟 TTL，只够完成当前任务
>
> 和标准 OAuth2 Token Exchange 的差异：
> - 我的 STS 是教学级内存/SQLite 实现，没有 JWT 签名（生产应该用 RS256 签名的 JWT）
> - 没有 refresh token 机制（生产该有）
> - 没有 OIDC 身份联邦（生产需要对接企业 SSO）
>
> 但核心安全语义是对的：权限收缩 + 最小权限 + 短时效。这三个原则构成了 Agent 系统区别于普通后端的安全新课题——Agent 是"自主决策的黑箱"，你不能让一个自主决策的实体拥有超过它需要的权限。

**加分点**：讲洋葱型防御三层——"为什么不在网关层一次性校验完？因为 Agent 系统多了一层不确定性——LLM 可能被注入攻击调不该调的工具。所以每层都要拦：网关层拦无效 Token，运行时层拦越权调用，工具层留审计记录。"

### 2.2 工具与执行类

#### Q4："工具调用失败了怎么办？Agent 怎么知道工具返回的是垃圾？"

**面试官在考察**：异常处理、鲁棒性设计。

**回答策略**（诚实 + 改进思路）：

> 当前实现的鲁棒性有三个层次：
>
> 1. **参数白名单**（`registry.py`）：执行前按 Schema properties 过滤多余参数。LLM 有时会传不在 Schema 里的字段（hallucinate 参数），白名单防止注入。
> 2. **工具沙箱**（`tools/sandbox.py`，R1）：超时控制 + 指数退避重试（1s→2s→4s，最多 3 次）+ 异常标准化，`registry.execute` 经 sandbox 执行，失败自动重试。
> 3. **LLM 兜底**（`single_agent_graph.py`）：generate_answer 节点里 call_llm 失败时，降级为直接拼接原始工具数据返回。
>
> 另外 R3 已补工具结果校验：`evaluate_results` 按结果质量标记 `needs_retry`（失败重试）/ `needs_more`（数据不足补充），不再是 noop。
>
> **还在演进的方向**（主动提，比"全做好了"更可信）：
> - **逐工具结果质量规则**：当前 R3 是通用校验，可深化为按工具定制（如"query_orders 必须返回至少 1 条""search_knowledge_base 的 rerank 分必须 > 0.5"），不达标自动重试或降级
> - **输出护栏深化**：R2 已有规则引擎（越权指令/敏感信息/缺失段落，block/warn/off），生产可加 JSON Schema 校验 + 小模型有害内容分类器

**面试官心理**：这个回答展示了"我知道哪里不完美、我知道怎么改"——比"全做好了"更可信。

#### Q5："你的 RAG 为什么用了四步（向量+BM25+RRF+重排）？一步向量检索不够吗？"

**面试官在考察**：检索系统设计能力、中文 NLP 理解。

**回答策略**：

> 一步向量检索有真实失败案例，是我实测出来的：
>
> **Case 1：MiniLM 中文召回弱**
> 问"广州航天合同有什么特殊条款？"
> → 纯向量 top1 结果是"历史延期记录.txt"，distance 0.9+
> → 根源：MiniLM 对"广州航天"和"合同"的语义向量不如关键词匹配精准
>
> **Case 2：专业术语失灵**
> "PEEK 材料 100% 全检条款" — MiniLM 可能不知道"PEEK"是材料名、"全检"是制造术语
>
> 四步检索的分工：
> 1. **向量召回**：覆盖语义相近但字面不同的查询（"交付期限"↔"交期要求"）
> 2. **BM25（jieba）**：补字面命中（"广州航天"必须出现在结果里）
> 3. **RRF 融合**：向量 distance（0-2+）和 BM25 score（0-50+）尺度不同，不能线性加权。RRF 只看排名位置——`1/(k+rank)`——统一尺度且免调参
> 4. **Cross-Encoder 重排（bge-reranker-base）**：双塔模型（向量+BM25）做粗排快但精度低，Cross-Encoder 做精排慢但精度高。取 top_k 候选让重排器精挑，这个速度/精度权衡是标准答案
>
> **但也要诚实说局限**：四步检索解决的是"语义匹配"问题，解决不了"结构化筛选"问题。比如"交期<7/30 AND 客户等级=A AND 工艺=3D打印"——RAG 做不到，需要 NL2SQL 或者结构化查询工具。当前 demo 用工具函数（`query_orders` 支持 status 和 customer_name 筛选）绕过了这个问题，但不够优雅。

**加分点**：讲 reranker 离线加载的坑——"huggingface_hub import 时固化了 `HF_HUB_OFFLINE` 到 constants，运行时设环境变量无效，必须直接 patch constants。这是真实踩的坑，花了半天排查。"

### 2.3 可观测性类

#### Q6："你的 Tracer 和 OpenTelemetry 是什么关系？为什么不直接用 OTel SDK？"

**面试官在考察**：是否盲目自研、是否有技术判断力。

**回答策略**：

> 设计思路是"OTel 同构但不是 OTel 实现"——接口对齐 OTel 的 Span/Tracer/Exporter 概念，但实现是轻量自研。原因：
>
> 1. **延迟批量导出**：Agent 场景有个特殊问题——业务代码（`llm_client.py`）在 `with tracer.span()` 退出后，还需要从 response 对象提取 token 用量写入 span.attributes。OTel 的 `start_as_current_span` 在 with 退出时立即 end 并导出，token 属性就丢了。我的方案是 in-memory Span 作事实源 + 整轮 query 结束统一 flush。
>
> 2. **零依赖开箱跑**：不装 opentelemetry 也能跑（默认 console 导出），装了切 `OTEL_EXPORTER=otel` 无缝升级到真 OTel。
>
> 3. **概念教学**：教学项目要展示"导出"的概念（把完成的 span 序列化到外部 sink），但不是必须依赖 OTel SDK。console exporter 就是一个最小可行的"导出"——结构化的 JSON 行，和 OTel 导出是同一概念。
>
> **如果面试官追问"生产会不会自研"**：不会，生产直接用 OTel SDK + Langfuse。但这次自研让我理解了 OTel 内部 SpanContext/TraceProvider/SpanProcessor 的工作机制，以后排 OTel 相关故障时我能看懂源码。

#### Q7："成本熔断你做到什么程度？"

**面试官在考察**：成本控制意识、工程化程度。

**回答策略**：

> 三个级别：
>
> 1. **正常记录**：每次 `call_llm` 自动记录 prompt_tokens + completion_tokens，按 provider 定价表（豆包 2.0/M、DeepSeek 1.0/M）计算费用
> 2. **预警**：累计费用达到预算的 80%，控制台打印预警（"剩余 ¥0.8"），但不阻断
> 3. **熔断**：累计费用达到预算的 100%，抛 `BudgetExceededError`，拒绝所有新的 LLM 请求
>
> 和 tracer 集成：每轮 query 结束输出费用摘要（含进度条 `[▓░░░░] 20%`），OTel 档下可随 span 导出到成本看板。
>
> **局限（主动提）**：
> - 按会话计费，不是按用户/租户——生产需要 CostTracker 加 `user_id` 维度
> - 预算设在代码环境变量（`LLM_BUDGET_LIMIT=5.0`），生产应该走配置中心
> - 熔断后没有自动恢复——生产应该加冷却时间（如"熔断 5 分钟后自动重置"）

### 2.4 缓存设计类

#### Q8："两级缓存的设计理由是什么？为什么不是一级？"

**面试官在考察**：缓存架构设计、命中率与成本的权衡。

**回答策略**：

> 两级缓存的定位完全不同：
>
> | | L1 精确缓存 | L2 语义缓存 |
> |---|---|---|
> | 存储 | SQLite | Chroma cosine 空间 |
> | 命中条件 | **完全相同**的 prompt（hash 匹配） | **语义相似**的问题（cosine distance < 0.20） |
> | 响应时间 | < 1ms | ~50ms |
> | token 消耗 | 0 | 0（跳过整图执行） |
> | 适用场景 | 相同问题重复问 | 换个说法问同一件事 |
>
> **为什么不是一级**：
> - 只用 L1：用户问"今天哪些订单紧急？"和"查一下今天的紧急订单"是同一件事但 hash 不同，L1 会 miss
> - 只用 L2：语义缓存命中精度不如精确缓存（cosine distance 可能有误判），而且每次查询都要 encode 到向量空间
>
> **关键设计决策**：语义缓存只对 `thread_id=None` 的独立问题生效。多轮对话里同一句话的答案依赖前文上下文，首轮缓存的结果不能直接复用——这是真和多轮打交道的经验。
>
> **阈值校准**：我用 MiniLM cosine distance 实测——完全相同 0.00 / 多标点 0.04 / 近义改写 0.17 / 较远改写 0.37 / 不相关 0.46+，默认 0.20 正好分隔。

### 2.5 安全与鉴权类

#### Q9："Agent 系统相比普通后端，安全上有什么新挑战？"

**面试官在考察**：安全意识、对 Agent 特有风险的认知。

**回答策略**：

> Agent 系统有三层普通后端没有的安全挑战：
>
> 1. **自主决策 × 权限放大**：普通后端的权限边界是明确的（一个 API 接口做什么不做什么是代码写死的）。Agent 自主决定调什么工具、看什么数据，如果 LLM 被 prompt injection 攻击，它可能调用不该调的工具。我的对策：洋葱型防御三层——网关层 Token 验证（STS 校验 Token 有效性）→ 运行时层 RBAC 权限校验 → **工具层二次验证**（`guard.py`），每一层都拦，不赌某一层完美。（诚实补充：当前 STS 是内存/SQLite 实现，无 JWT 签名，生产应换 RS256 签名 JWT——见 Q3。）
>
> 2. **黑箱审计**：Agent 一个查询背后可能 5 次 LLM 调用 + 3 次工具调用，没有 trace 就无法追溯。我的对策：一个请求一个 Trace ID，LLM 调用记 span（含 token 用量），工具调用记 span（含参数和结果摘要），审计日志记主体/操作/目标/结果。出问题时按 trace_id 还原完整调用链。
>
> 3. **Token 放大链**：单 Agent 模式只一个 Token，多 Agent 模式下 Supervisor 要把 Token 交换给子 Agent。如果子 Agent 又下钻调更多 Agent，Token 逐级交换形成一条"权限放大链"。我的对策：Token Exchange 每次交换强制权限收缩（子权限 ⊆ 父权限），且子 Token 短时效（5 分钟），泄漏了影响有限。
>
> 这三个挑战在普通后端不存在或程度很低，但在 Agent 系统中是核心安全问题。

**加分点**：提到 OWASP Top 10 for LLM Applications——prompt injection、insecure output handling、sensitive information disclosure、excessive agency——并对应到自己的防御措施。

## 三、生产发布后可能出现的现网问题 — 逐场景预案

> 这部分是面试中"被问现网问题时"的应对弹药。面试官问"你这个系统如果上线了，可能会出现什么问题？"——这是在考察你的生产意识。

### 场景 1：Agent 突然不回答了（LLM 调用全部失败）

**现象**：用户问问题，Agent 返回"所有 provider 均失败"

**排查路径**：
1. 查 trace → 看哪个 provider 先失败 → 是否全部 provider 都失败？
2. 查审计日志 → 最后一次成功的 LLM 调用是什么时候？
3. 查 API Key → 是否过期/余额不足？
4. 查网络 → 是否代理挂了（Windows cc-switch 退出后注册表残留死代理）？

**预防措施（当前有/没有）**：
- ✅ 主备 fallback：一个挂了自动切下一个
- ✅ trust_env=False：绕系统代理
- ⬜ 健康检查端点：`/health` 包含 LLM 连通性检查（当前只返回 ok）
- ⬜ 告警：provider 失败率超过阈值自动通知

**面试话术**："主备 fallback 是基础，但生产还要加熔断后的自动恢复、健康检查端点的 LLM 连通性测试、provider 失败率告警。"

### 场景 2：LLM 成本突然飙升

**现象**：单轮对话 token 消耗从正常的 2000-3000 跳到 20000+

**排查路径**：
1. 查 trace → 单轮调了几次 LLM？是否有死循环？
2. 查 messages 长度 → 是否上下文无限增长？
3. 查语义缓存命中率 → 是否缓存失效？
4. 查 tool_results → 工具返回是否异常大（导致 messages 膨胀）？

**预防措施**：
- ✅ 5 轮安全阀：`iteration >= 5` 强制结束
- ✅ 预算熔断：超预算抛异常
- ✅ 预警：80% 预算时打印警告
- ✅ **上下文压缩（R4）**：`CONTEXT_MAX_CHARS` 触发 summarization buffer 压缩，保留 system + 最近 6 条，中间 LLM 摘要替代
- ⬜ 硬截断（保留最近 N 条，旧丢弃）：作为压缩兜底，未做
- ⬜ 缓存命中率监控

**面试话术**："Agent 的成本控制需要三道防线——迭代上限防死循环、上下文截断防膨胀、预算熔断防失控。当前做了 1、3 和上下文压缩（R4），硬截断兜底还没做。"

### 场景 2b：上下文压缩触发后答案质量下降

**现象**：长对话触发 summarization buffer 压缩后，Agent 回答遗漏早期关键信息

**排查路径**：
1. 查 trace → 压缩发生了几次（`compression_count`）？压缩摘要是否丢了关键约束？
2. 查 `CONTEXT_KEEP_RECENT` → 保留的最近消息数是否太少
3. 查压缩摘要 → LLM 生成的摘要是否准确保留了业务约束（如合同 SLA、客户等级）

**预防措施**：
- ✅ 保留 system + 最近 N 条（R4，`CONTEXT_KEEP_RECENT=6`）
- ⬜ 压缩质量校验：摘要生成后校验关键业务字段是否保留
- ⬜ 压缩次数监控与告警（长对话预警）

**面试话术**："上下文压缩是双刃剑——省 token 但可能丢上下文。R4 做了保留 system + 最近 N 条 + LLM 摘要，生产还应加压缩质量校验和压缩次数监控。"

### 场景 3：RAG 检索结果"答非所问"

**现象**：用户问"广州航天合同"，Agent 返回了"深圳精密合同"的内容

**排查路径**：
1. 查 trace → tool:search_knowledge_base 的 span，看返回了哪些片段
2. 查 rerank score → 是否所有片段 rerank 分都很低（< 0.5）？
3. 查向量库 → 文档是否已入库？分块是否合理？
4. 查 BM25 命中 → "广州航天"是否在文档中（可能是分词问题——"广州"和"航天"被拆成两个词）

**预防措施**：
- ✅ 四步混合检索：BM25 补向量中文召回弱
- ✅ Cross-Encoder 重排：精排过滤无关结果
- ⬜ **检索质量阈值**：rerank 分全 < 0.5 时标记为"低质量检索"，不喂给 LLM（仍未做）
- ⬜ 检索回归测试：用 ground truth Q&A 对做持续评估（R6 eval/ 已有基础，未接 CI）

**面试话术**："RAG 的质量保障需要检索 + 生成双环节。检索端四步混合检索 + 重排是基础，但还不够——应该加'无结果降级'（告诉用户'没找到，换个说法试试'），以及'检索质量阈值'（全低分时不强行喂给 LLM 编造答案）。"

### 场景 4：多 Agent 模式下子 Agent 鉴权失效

**现象**：审核 Agent 调了不该调的库存工具（越权）

**排查路径**：
1. 查审计日志 → trace_id 对应的 Token Exchange 记录 → 子 Token 的 permissions 是否正确？
2. 查 guard.py → check_tool_permission 是否被调用？
3. 查 registry.execute → token 参数是否传了 None？
4. 查单 Agent 模式 → 是否走了单 Agent 模式（`token=None` 绕过鉴权）？

**预防措施**：
- ✅ RBAC 在工具层强制：`guard.py` + `registry.execute` 双重校验
- ✅ 审计日志 trace_id 贯穿：可以逐条还原鉴权链路
- ✅ **多租户强制（R8）**：`FORCE_TENANT=true` 时无 tenant_id 拒绝，数据层租户过滤
- ⬜ `FORCE_AUTH`：生产环境强制所有模式走鉴权（**仍未做**——注意区分：R8 是 FORCE_TENANT 多租户，不是 FORCE_AUTH 强制鉴权）

**面试话术**："鉴权是 Agent 系统最关键的安全防线。关键在于'默认拒绝'而非'默认放行'。当前有一个已知风险——单 Agent 模式 token=None 绕过鉴权——生产必须加 FORCE_AUTH 开关。R8 已补多租户强制（FORCE_TENANT），但强制鉴权（FORCE_AUTH）仍未做。"

---

### 场景 5：状态持久化文件损坏，用户对话丢失

**现象**：`checkpoints.db` 损坏，用户重启后无法恢复对话

**排查路径**：
1. 查 `demo/data/checkpoints.db` → SQLite 文件完整性（`PRAGMA integrity_check`）
2. 查磁盘空间 → 是否磁盘满导致写入失败？
3. 查并发 → 是否多进程同时写同一个 db（SQLite 单写者限制）？

**预防措施**：
- ✅ SqliteSaver 落盘持久化
- ⬜ SQLite WAL 模式（Write-Ahead Logging）：提高并发安全性
- ⬜ 备份策略：定期备份 checkpoints.db
- ⬜ 降级策略：db 损坏时自动切到 memory 模式（至少本轮可用）

**面试话术**："状态持久化的关键是'优雅降级'。db 损坏不应该导致整个 Agent 不可用，应该自动切到无状态模式，同时告警通知运维。SQLite 在并发场景下要开 WAL 模式。"

---

### 场景 6：语义缓存"错误命中"——不同问题返回了相同答案

**现象**：用户问"库存够不够"返回了"排产建议"，因为某个近义改写错误匹配到了之前的缓存

**排查路径**：
1. 查 trace → `cache:lookup` span，看 result=miss 还是 hit，以及 distance 值
2. 查缓存内容 → 被命中的那条缓存对应的原始问题是什么？
3. 调阈值 → 当前 threshold=0.20 是否太宽？

**预防措施**：
- ✅ 阈值校准：实测 0.20 分隔同义改写（0.17）和不相关（0.46+）
- ✅ 多轮对话跳过缓存：`thread_id` 非空不查语义缓存
- ⬜ 命中校验：后台异步调 LLM 验证缓存答案对当前问题仍正确
- ⬜ 缓存版本：Prompt 变更时自动 invalidate

**面试话术**："语义缓存的核心风险是'假阳性'——语义相似但业务含义不同。缓解措施：阈值选在"同义 vs 不相关"的统计分界点、多轮对话跳过缓存、后台异步校验。生产换 bge-large-zh + Redis 会有更好的中文判别力。"

---

### 场景 7：Docker 部署后 reranker 首次请求超时

**现象**：容器启动后第一个 RAG 查询卡死 30 秒

**排查路径**：
1. 查网络 → reranker 模型（~1.1GB）是否本地已缓存？
2. 查 volume 挂载 → `~/.cache/huggingface` 是否挂载进容器？
3. 查 HF_HUB_OFFLINE → 离线模式下模型不存在会报错

**预防措施**：
- ✅ docker-compose 模型缓存挂载：`~/.cache/huggingface:/root/.cache/huggingface`
- ✅ HF_ENDPOINT 镜像加速：`https://hf-mirror.com`
- ✅ 离线优先：`HF_HUB_OFFLINE=1` patch

**面试话术**："首次加载重模型的延迟有两个解法——预热（容器启动时预加载）和缓存持久化（volume 挂载）。当前做了缓存挂载，但没做启动预热。生产应该在 health check 通过前完成模型预热。"

## 六、面试官可能问的对比题

### "你这个和 LangChain 的 create_react_agent 有什么区别？"

> "LangChain 的 create_react_agent 一行代码就能跑一个 Agent。但它是一个黑箱——你不知道内部状态怎么流转、工具怎么选择、错误怎么处理。
>
> 我的做法是先手写 ReAct 循环（Week 1-2），理解了 LLM→判断→执行→回传的原语，再用 LangGraph 替代手写循环。我特意保留了手写版和 LangChain 版的对照代码（`scripts/week3/langgraph_agent.py` 手写 vs `langgraph_agent_lc.py` LangChain 版），目的是证明'知其然且知其所以然'。
>
> 另外 create_react_agent 是一个单 Agent，我的系统在此基础上加了多 Agent Supervisor、Token Exchange 鉴权、全链路观测——这些是企业级需求，create_react_agent 不管。"

### "你这个和 AutoGPT/CrewAI 有什么区别？"

> "AutoGPT 和 CrewAI 是'自动驾驶'模式——你给一个终极目标，Agent 自己拆解、自己执行、自己判断完成。优点是灵活，缺点是可控性差（可能跑偏、成本不可预测）。
>
> 我的系统的设计理念更接近'辅助驾驶'——Agent 在 LangGraph 状态图规定的框架内自主决策（选哪些工具、调什么顺序），但框架本身是确定的（4 个节点、条件边路由、5 轮上限）。这种设计更适合企业场景——需要可预测、可审计、可控制。
>
> 另外 CrewAI 的多 Agent 是角色扮演（你设一个'审核专家'角色，它自动生成对应的 Prompt 和行为），黑箱程度更高。我选择了显式的 Supervisor 模式——每个 Agent 的 Prompt、工具权限、鉴权令牌都是显式定义的，透明可控。"

### "如果让你重新设计，你会改什么？"

> "三个改动：
>
> 1. **先写测试**：工具层和图的测试应该在代码之前。当时训练节奏快，每周要出 Demo，测试被牺牲了。如果是正式项目，我会 TDD——先定义工具的行为规范（输入输出），再实现。
>
> 2. **工具层从第一天就走 MCP 协议**：R5 已补 MCP client（stdio 子进程通信），但默认运行时仍走函数调用 fast path（`MCP_MODE=local`）。如果一开始就走协议调用，隔离性、可扩展性、安全性都会更好。当时选了 fast path 是为了降低调试复杂度——这个取舍在训练阶段合理，但在生产项目中不该。当前 `MCP_MODE=mcp` 即可切换。
>
> 3. **评估体系同步建设**：R6 已补 `eval/` 模块（10 组 ground truth + 加权指标 + runner，回归基线 7/10）。但初始的评估是 Week 4 才补的（RAGAS 脚本），应该在 Week 2 有了第一个 RAG 就建基线。没有基线就无法量化'改这个参数到底有没有效果'——这是最大的工程教训。"

## 七、技术弹药库（被追问时的深度储备）

### 7.1 能讲清楚原理的协议/标准

| 协议/标准 | 掌握程度 | 能讲什么 |
|----------|---------|---------|
| **RFC 8693**（OAuth 2.0 Token Exchange） | 核心语义掌握，有代码实现 | subject_token → exchanged token、权限收缩、scope down、短时效 TTL |
| **OpenTelemetry** | 同构实现，理解内部机制 | SpanContext/TraceProvider/SpanProcessor/SpanExporter、延迟批量导出、OTLP gRPC |
| **MCP**（Model Context Protocol） | 协议理解到位，有 server 构建 + client 子进程实现 | stdio/SSE 通信、tools/list + tools/call、工具发现与执行分离、`MCP_MODE=mcp` 走子进程隔离（R5） |
| **OpenAI Function Calling** | 实战级 | tool_call_id 配对回传、parallel tool calls、JSON Schema 约束 |
| **RRF**（Reciprocal Rank Fusion） | 有代码实现 | `1/(k+rank)` 公式、k=60 的理由（平滑极端排名差）、与线性加权的对比 |

### 7.2 能解释设计决策的取舍

| 决策 | 选了什么 | 为什么选 | 另一种方案的优劣 |
|------|---------|---------|----------------|
| 编排框架 | LangGraph | 状态图显式、可测试、有 checkpointer | 手写 while — 简单但不持久；CrewAI — 黑箱 |
| 鉴权方案 | STS Token Exchange + RBAC | 权限收缩 + 最小权限，符合 Agent 安全需求 | JWT — 更标准但单 Token 无法表达权限收缩链 |
| 观测方案 | 自研 Tracer + OTel 同构 | 延迟批量导出适应 Agent 场景 | 直接用 OTel SDK — 标准但无法解决"with 后写属性"问题 |
| 缓存方案 | L1（SQLite）+ L2（Chroma） | 精确 + 语义互补 | Redis — 更适合生产但增依赖 |
| 路由方案 | 关键词路由 | 零成本、确定性 | LLM 路由 — 更灵活但有成本 |
| 工具执行 | 函数直调 + 沙箱（R1 超时重试） | 默认 fast path 降低复杂度，沙箱兜底；MCP 子进程（R5）已具备但默认不启用 | 真 MCP 子进程 — 隔离性好但调试难（`MCP_MODE=mcp` 可切换） |

### 7.3 真实的踩坑清单（证明"真写代码"）

| # | 坑 | 影响 | 解法 | 面试价值 |
|---|------|------|------|---------|
| 1 | Windows 控制台 GBK 编码不了 emoji | 输出乱码/崩溃 | `sys.stdout.reconfigure(encoding="utf-8")` | 跨平台工程意识 |
| 2 | cc-switch 退出后注册表残留死代理 | LLM 调用 SSL EOF | `trust_env=False` | 网络问题排查能力 |
| 3 | huggingface_hub import 时固化 HF_HUB_OFFLINE | 运行时设 env 无效 | patch constants | 源码级调试能力 |
| 4 | Chroma ONNX 模型 S3 下载国内极慢 | 5 分钟 9% | Clash 代理 `127.0.0.1:3450` | 网络环境意识 |
| 5 | Chroma 1.1.1 旧库加载 panic | rust binding crash | 删除重建 chroma_db | 版本兼容性排查 |
| 6 | 豆包 coding plan 端点用 /api/v3 会额外收费 | 成本浪费 | 仔细读文档，用 /api/coding/v3 | 细心和成本意识 |

## 八、面试结束时的"反问"建议

当面试官问"你有什么问题吗"时，用以下问题展示你的深度：

1. **"团队目前的 Agent 系统，编排层用的是什么框架？多 Agent 之间怎么协调的？"**
   — 展示你对编排有深度理解，不是只会 LangGraph

2. **"Agent 系统的安全审计怎么做？有没有遇到过 Token 泄漏或 prompt injection 的问题？"**
   — 展示你有安全意识

3. **"LLM 调用的成本怎么控制的？有没有做过智能路由——简单问题调小模型、复杂问题调大模型？"**
   — 展示你有成本意识

4. **"Agent 的评估体系怎么建的？是人工评分还是自动化？有没有持续评估的 pipeline？"**
   — 展示你关注质量闭环
