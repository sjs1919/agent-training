## 重点提炼：三梯队

### 第一梯队 · 核心增量（必须深挖，现有路线盲区）

#### ① Harness 工程（主题 6、7）- 最核心

**要搞懂的问题：**

- **Harness 是什么**：区别于 Agent 本身，Harness 是包裹 Agent 的**控制层/脚手架**--编排、状态管理、错误恢复、可观测、权限、成本、评估的外层工程。类比：Agent 是引擎，Harness 是底盘 + 仪表盘 + 安全带。没有 Harness 的 Agent 是"能跑但失控"的引擎。
- **为什么"能运行"≠"可控运行"**：Demo 跑通 happy path 不等于生产可控。排产场景生产要面对：模型非确定性输出（同一批订单排出不同优先级）、工具调用失败（查库存超时）、长上下文漂移、成本失控、越权调用。Harness 是把这些不可控收敛成可控的工程层。
- **Harness 的核心组件**：编排/状态机、工具执行沙箱与重试、上下文管理（压缩/分段）、检查点与恢复、可观测（trace/metric/log）、权限网关、成本预算与熔断、评估与护栏（guardrails）。
- **MVP->PMF 的 Harness 演进**：MVP 最简 Harness（while 循环 + print + try-catch）能验证什么？PMF 阶段哪些能力是"上线前必须有"（权限、可观测、重试），哪些是"规模化后才有"（多租户隔离、SLA、评估闭环、成本治理）。关键判断：不是所有 Harness 能力都要一次建齐。
- **融合到现有 demo**：week3 LangGraph 状态图 = Harness 编排层雏形；week4 鉴权 = Harness 权限层；week5 可观测 = Harness 观测层。**现有路线有零件没装配--Harness 是把零件装成系统的概念框架**。升级动作：不新增模块，而是用 Harness 框架重新组织 week3-5 已有代码的理解和文档。

#### ② 业务数据包设计（主题 3）

**要搞懂的问题：**

- **业务数据包是什么**：针对一个业务场景，预先组织好的、Agent 可消费的数据集合--结构化表（订单/物料/设备/交期）+ 非结构化文档（工艺卡/合同特殊条款）+ 工具接口（查库存/查设备负载/算交期）。**数据包决定 Agent 能"办"什么事**，是"能回答"到"能办事"的数据底座。
- **筛选/比较/关联为什么难**（接主题 2）：纯向量检索处理不了"交期 7/30 前、A 级客户、3D打印工艺、按设备空闲排序"这种多条件结构化筛选--需要 NL2SQL 或工具编排，而非 RAG。这是 RAG 的能力边界，也是主题 2 的真正落点。
- **按场景的数据包设计模式**：

  | 场景类型 | 数据包形态 | 排程排产里的例子 |
  |---------|-----------|----------------|
  | 问答型 | RAG 文档包 | "深圳精密的合同有什么特殊条款" -> 检索合同 |
  | 筛选/比较型 | 结构化表 + 查询工具 | "交期最紧的 3 单 + 对应设备空闲" -> 工具编排 |
  | 推荐型 | 混合（结构化过滤 + 语义匹配） | "和历史上延期案例相似的当前订单" -> 先过滤后语义匹配 |
  | 流程型 | API 工具集 + 状态机 | "排一版今日产线计划" -> 工具调用链 + 状态 |

- **融合到现有 demo**：week2 的 customers.csv/orders.csv 是最简结构化数据包，但缺"按场景设计数据包"的方法论。升级动作：把现有 orders/inventory/machines/customers + 合同知识库，按上述四类场景重新组织成"排产业务数据包"，并在文档里写明每类场景的数据包构成。

#### ③ 长任务步骤合并/跳过（主题 5）

**要搞懂的问题：**

- **成因**：长上下文下注意力稀释；模型倾向"省事"合并相邻步骤；todo 列表过长时跳过中段；工具结果过长导致模型"误以为已完成"。
- **对策**：强制结构化 todo（每步显式勾选完成）、检查点（持久化中间状态可恢复）、子任务分解（拆给子 Agent）、步骤校验（每步后校验产物而非依赖模型自述完成）、上下文压缩（保留关键决策，丢弃冗余工具输出）。
- **融合到现有 demo**：week3 LangGraph 有 `iteration>=5` 强制结束，但没处理"模型在 5 轮内偷懒跳步"（例如排产时跳过查设备负载直接给结论）。week2 day4 的 Todo-driven Agentic RAG 是对策雏形。升级动作：在排产 Agent 的 `select_and_execute` 节点后加步骤校验--每步工具结果是否真的拿到了（而非模型自述），todo 项是否被显式勾选。

### 第二梯队 · 新视角补强

#### ④ 不切换场景，能力回炉现有 demo（主题 4）
课程用 Vibe Coding 搭租房经纪人助手是**教学方法**，吸收其手法（快速搭建、迭代式对话开发），但落地到现有 week3 排程排产 Agent 上验证，不另起房产案例。重点是把课程的 Agent 搭建套路用来回炉、优化现有 demo，而非复制一个跨行业的玩具。

#### ⑤ MVP->PMF + 制造业岗位结合（主题 7、9）
现有路线是纯技术演进，缺产品落地视角。重点：用排产 demo 走一遍 Harness 的 MVP->PMF 演进（哪些能力上线前必须有、哪些规模化后才有）；把制造业岗位（排产计划员、车间调度、质检员）的工作拆解成 Agent 可承担的子任务，对齐 [`hangye/`](../hangye/) 行业报告。

## 行动建议

1. **week4-5 进行中**：把课程主题 6/7（Harness）作为 week5「可观测 + 业务匹配」的**概念升级**--不是新增工作，而是把 week3-5 已有的 LangGraph / 鉴权 / 可观测零件，用 Harness 框架重新组装理解。
2. **主题 3/5**：在现有排程排产 demo 上做"业务数据包重组 + 长任务步骤校验"的升级实验，不新增场景。
3. **上课节奏**：上课前重点预习 Harness 概念（主题 6/7），上课时带着"现有 week3-5 零件如何装配成 Harness"的问题听；课程里的房产案例只听方法论，不照搬场景。
4. **产出**：课程结束后，把 Harness 组件清单整理进 [`企业级Agent开发加速路线`](../00_总纲_路线.md) 的 week5 段落，作为路线升级；升级代码落在现有 `scripts/week3-5/`，不新增场景目录。
