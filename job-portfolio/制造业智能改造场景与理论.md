> 基于 agent-training 4 周训练成果 + 3D 打印/CNC 排程排产业务，梳理 6 个业务环节的智能改造场景、理论支撑、线上实战问题
> 作为简历"企业 Agent"亮点的深度支撑 -- 面试时讲"我对制造业各环节智能改造的系统思考与踩坑预判"

> 训练能力源码锚点见 `agent-training经验与面试亮点.md`

## 总览：6 环节 × 训练能力映射

| 业务环节 | 智能改造核心 | 对应训练能力 | 源码锚点 |
|----------|-------------|-------------|----------|
| 1. 订单接入评审 | 非结构化接单 → 可行性初评 | Function Calling + ReAct + Prompt 工程 + LCEL 解析 | week1 day2/day3, week4 lcel |
| 2. 物料库存 | 缺料预测 → 采购触发 | Function Calling + RAG + 参数白名单 | week1 day2, week2 day1, week3 tool_registry |
| 3. 设备产能 | 负载调度 → 瓶颈识别 | 多 MCP Server + 状态图路由 + 并行工具调用 | week3 langgraph_agent |
| 4. 生产执行进度 | 异常监控 → 主动告警 | MCP Resource + 审计 Trace ID + 事件驱动 | week3, week4 audit_logger |
| 5. 客户合同 | 条款研判 → 风险评估 | 混合检索 + Rubric-checked RAG + RAGAS | week2 day2, week4 rubric/ragas |
| 6. 调度决策 | 多 Agent 协作排产 | Supervisor 编排 + Token Exchange 鉴权 + RBAC | week4 supervisor/token_exchange |

一条主线：环节 1-5 是单 Agent / 单能力改造，环节 6 是多 Agent 协作把前 5 个能力编排成端到端调度决策系统。递进关系和训练 4 周完全同构。

## 环节 1：订单接入评审

### 场景
客户通过电话/邮件/系统下单，需求含产品、数量、交期、材料、工艺等。传统流程：客服录单 → 调度查库存 → 查产能 → 人工评估可行性，耗时长且字段易错。智能改造：Agent 自动解析非结构化订单（邮件/语音转文本），调用订单/库存/设备工具初评可行性，输出接单建议与预计交期，人工只做最终确认。

### 相关理论
- **Function Calling + ReAct 循环**（`week1/day2_function_calling.py:251-333`）：Agent 自主决策调用 `query_orders` / `query_inventory` / `query_machine_load`，2-3 轮完成评估
- **非结构化输入结构化**（`week4/lcel_extract_json_chain.py:72-80`）：LCEL 链 `prompt_extract | llm | StrOutputParser()` 把客户自由文本提取为结构化订单字段
- **三层 Prompt 工程**（`week1/day3_system_prompt.py:46-55`）：system 层注入调度专家角色 + 安全规则（防编造订单号），scenario 层接单场景，user 层隔离
- **JSON Schema 输出约束**：接单建议结构化输出（`week1/day3_system_prompt.py:154-176`，注意是 Prompt 级非 strict，生产用 `response_format`）

### 线上可能遇到的问题
1. **模糊表述解析**：客户说"加急""尽快""跟上次一样"-- LLM 需 Few-shot + 术语表对齐，不能直接当确定交期
2. **口头需求与系统字段映射偏差**：需 HITL（Human-in-the-loop）确认环节，Agent 给建议、人拍板
3. **Agent 幻觉编造订单号/库存**（Week1 真实风险）：必须 System Prompt 安全规则 + 工具返回值校验，不能让 LLM 自己"补全"数据
4. **高峰期并发接单**（`week2/day4_agentic_rag.py:46-49` 全局状态非线程安全教训）：生产需封装为实例级状态，否则并发崩
5. **订单字段与 MES 不一致**（vibe-coding api-client 不对齐教训）：接单 Agent 输出字段必须与下游 MES 字段契约对齐，否则流转断裂
6. **历史订单复用**：老客户复购应优先匹配历史订单模板，但需校验工艺/材料是否变更

## 环节 2：物料库存

### 场景
排产前校验材料库存是否满足订单，计算用量、安全库存、采购周期。传统人工查库存 + 算用量 + 盯补货。智能改造：Agent 调用库存工具 + BOM 计算需求，预测缺料时间点，自动生成采购建议。

### 相关理论
- **库存工具调用**（`week1/day2_function_calling.py` query_orders 模式可迁移到 query_inventory；`week3/resource_server.py` 的 `query_inventory` 工具）
- **物料规格/采购周期 RAG**（`week2/day2_hybrid_rerank.py:247-259`）：混合检索物料文档，避免纯向量召回错物料
- **参数白名单防御**（`week3/tool_registry.py:156-162`）：执行前按 Schema 过滤 LLM 传的多余参数，防库存查询注入非法字段
- **Todo-driven 规划**（`week2/day4_agentic_rag.py:74-106`）：多物料校验时 Agent 规划清单逐项查

### 线上可能遇到的问题
1. **账实不符**：系统库存与实物不一致（领料未登记/损耗未录），Agent 基于错误数据决策 -- 需库存校验机制 + 异常标记
2. **单材料硬约束**：一个版子只排一种材料、一台设备同时只一种材料（业务硬规则），Agent 必须理解，不能跨材料混排
3. **耗料计算不能用 LLM 算**：耗材量按平衡块位置算、600/800 机型截面积已实测、液位仅校验 -- 这类确定性公式必须调确定性算法，LLM 只做决策不做计算
4. **BOM 变更不同步**（`week2` 文档与代码不同步教训）：BOM 改了知识库没更新，Agent 按旧 BOM 算 -- 需实现后核对源头机制
5. **物料单位不统一**（kg/卷/桶/件）：需术语表对齐（`week2` 60+ 术语表思路），否则用量计算错
6. **采购周期不确定**：供应商交期波动，需概率预估而非点估计，安全库存要动态调整

## 环节 3：设备产能

### 场景
排产匹配设备（3D 打印 330+/尼龙 60+/金属 50+/CNC 250+，7+ 品牌），考虑设备类型、负载、预计空闲。传统人工排程靠经验。智能改造：Agent 调用设备工具，按类型 + 负载 + 交期优化排程，识别瓶颈设备，输出可执行排产方案。

### 相关理论
- **多 MCP Server 按域拆分**（`week3/order_server.py` + `resource_server.py`）：设备工具归资源域 Server，独立演进，对 LLM 透明
- **状态图条件边路由**（`week3/langgraph_agent.py:530-558`）：设备数据不够继续查、够了生成排程，`should_continue` 三分支
- **并行工具调用**（`week3/langgraph_agent.py:359-418` select_and_execute 支持 Parallel Tool Calling）：并行查多台设备负载
- **LLM 启发式 + 规则约束**：LLM 做排程启发式，硬约束（机型/材料/交期）用规则校验，不交给 LLM 自由发挥

### 线上可能遇到的问题
1. **设备 API 不稳定**（7+ 厂商 API：联泰/Formlabs/拓竹/黑格/惠普/华曙/Unicorn）：需主备 fallback（`week1/day1_api_basics.py:115-144`）+ 重试 + 熔断，单厂商挂不能瘫
2. **设备状态实时性**：故障/维修/上机中状态延迟上报，排程基于过期数据 -- 需 MQTT/WebSocket 实时上报 + 数据新鲜度校验
3. **排程冲突仲裁**：多订单争同一设备，需锁机制/优先级仲裁，Agent 不能并行占同一设备
4. **瓶颈设备误判**：LLM 可能误判瓶颈，需规则校验（负载率/队列长度阈值）+ 历史瓶颈数据对照
5. **机型能力差异**：不同机型截面积/精度/材料支持不同，排程需能力匹配矩阵，不是"任意设备排任意单"
6. **集群维度**：设备分集群（group_unique_code），单集群有上限，富海产区集中度突破需多集群负载均衡 -- 排程需感知集群边界

## 环节 4：生产执行进度

### 场景
订单上机后跟踪生产环节（CNC 加工/质检/热处理/焊接），异常（超期/故障/质检失败/坏件）需上报应对。传统靠人工盯 + 凌晨电话（summary.md 提到建立前需凌晨人工盯电话）。智能改造：Agent 监控生产状态，异常主动告警 + 触发应对流程（重排/补料/报废登记）。

### 相关理论
- **MCP Resource 原语**（Week3 教训：只用了 Tools，只读数据用 Resource 更语义化）：生产状态作为 Resource 订阅，而非轮询工具
- **审计日志 Trace ID**（`week4/auth/audit_logger.py:24,34-47`）：一个订单一个 Trace ID，全链路跟踪生产环节流转
- **事件驱动 + Agent 分诊**：异常事件触发 Agent 评估应对（重排 vs 补料 vs 报废）
- **状态机管理**（`week3/langgraph_agent.py` StateGraph 思路迁移到订单状态机）：订单状态流转显式化，防止非法跳转

### 线上可能遇到的问题
1. **进度数据滞后**：设备上报延迟，Agent 基于过期进度决策 -- 每条数据带时间戳 + 新鲜度校验，过期数据降权
2. **异常分类难**：故障/缺料/质检失败应对路径不同，需多 Agent 分诊或路由分类（`week4/agents/agent_router.py` 思路）
3. **误报/漏报**：阈值敏感，可借鉴 RAGAS 评估思路（`week4/ragas_eval.py`）对异常检测做 precision/recall 量化
4. **坏件口径不一**：整版失败（`oc_printer_type_setting.product_num`, status=4）+ 零件失败（`product_failing_num`），不用入库报废口径 -- Agent 登记坏件必须用对口径，否则统计失真
5. **链路任务无耗材**：链路任务（打印前准备）失败无耗材无坏件，耗材只来自真正打印任务 -- Agent 核算成本时必须区分链路任务 vs 打印任务
6. **字段映射易误用**：`oc_printer` 的 `unique_sign`=设备唯一编码、`group_unique_code`=集群，Agent 查设备必须用对字段
7. **状态机非法跳转**：Agent 不能把"生产中"直接改"已完成"，需校验前置环节（质检通过）

## 环节 5：客户合同

### 场景
接单/排产需考虑客户等级（A/B/C）、信用分、延期率、合同特殊条款（延期赔付 0.5%/日、航天件全检+报废、加急绿色通道）。传统人工翻合同。智能改造：RAG 检索合同条款 + Agent 综合客户信用评估订单风险，Rubric 校验不漏关键条款，输出风险评级（高/中/低）。

### 相关理论
- **混合检索四步管线**（`week2/day2_hybrid_rerank.py:247-259`）：BM25 字面 + 向量语义 + RRF 融合 + Cross-Encoder 重排 -- 合同条款检索必须混合，纯向量召回弱
- **Rubric-checked RAG**（`week4/rubric_checked_rag.py:51-68,153-205`）：4 条 Rubric（grounded/complete/no_external/cited）逐条检查，不达标反馈修订，最多 3 轮 -- 合同条款涉及钱和解约权，漏一条出事，后验拦截最硬
- **RAGAS 评估**（`week4/ragas_eval.py:118-307`）：faithfulness/answer_relevancy/context_precision/context_recall 量化检索质量
- **客户信用工具**（`week2/week2_agentic_rag_agent.py:91-104` query_customer）：结构化查询客户等级/信用/延期率

### 线上可能遇到的问题
1. **合同变更不同步**（`week2` 文档与代码不同步、Week2 G13 完成度 9% 教训）：合同改了知识库没更新，Agent 按旧条款研判 -- 需变更触发重建索引 + 实现后核对源头
2. **检索漏关键条款**：纯向量对"广州航天精工合同"top1 常召回"历史延期记录"（Week2 真实） -- 必须混合检索 + 重排，且 Rubric 兜底
3. **LLM 误读条款**：赔付比例/解约权/全检要求理解偏差 -- Rubric 后验拦截 + 关键数字回查原文
4. **合同隐私与鉴权**：客户合同敏感，不同角色可见不同合同 -- 需 Token Exchange（`week4/auth/token_exchange.py`）权限收缩，审核 Agent 只能看授权范围
5. **历史延期案例归因**：`week2/data/历史延期记录.txt` 5 个真实案例（CNC 主轴故障/物料延迟/质检返工）需持续积累，案例库是排产研判的关键知识资产
6. **客户等级动态变化**：A/B/C 等级随延期率变化，Agent 查询需实时，不能缓存过期等级

## 环节 6：调度决策（多 Agent 协作）

### 场景
综合订单/库存/设备/客户/合同，决策"今天先做哪些订单"。传统靠调度员经验。智能改造：多 Agent 协作 -- Supervisor 编排，审核 Agent 评估订单风险（客户信用+合同条款），生产 Agent 评估产能可行性（物料+设备+交期），鉴权隔离各 Agent 权限，审计全链路追溯，输出优先级排序供人确认。

### 相关理论
- **Supervisor 五步编排**（`week4/supervisor_agent.py:131-189`）：route → setup_auth → dispatch_review + dispatch_production → aggregate → audit_report
- **Token Exchange 权限收缩**（`week4/auth/token_exchange.py:74-99`，RFC 8693）：父 Token 换受限子 Token，`:86-88` 逐条校验子权限 ≤ 父权限，5 分钟短时效 -- 审核 Agent 只能看客户信息不能改订单状态，生产 Agent 只能查库存设备不能看客户信用
- **RBAC 5 角色矩阵**（`week4/auth/token_exchange.py:26-33`）：admin/scheduler/reviewer/operator/viewer 各持不同工具集
- **审计 Trace ID**（`week4/auth/audit_logger.py:50-64`）：决策链路不可否认，事后可追溯"为什么这个订单排了第一"
- **条件边路由**（`week3/langgraph_agent.py`）：数据不够继续查，够了汇总

### 线上可能遇到的问题
1. **多 Agent 协调成本**（`week4/README.md` 核心认知 5：多 Agent 代价）：额外路由编排 + 结果聚合，不是所有场景值得用 -- 简单查询用单 Agent，复杂调度才上 Supervisor
2. **Supervisor 硬编码**（`week4/supervisor_agent.py:148` 写死 sample_orders）：生产必须改动态查询，从路由结果/订单库取真实订单
3. **路由局限**（`week4/agents/agent_router.py:27-31` 纯关键词）：复杂意图需升级 LLM 路由，关键词路由会误分
4. **子 Agent 设计先行实现滞后**（`week4/agents/review_agent.py:91-99` review_order 未接 LLM 只返回 pending_review）：Prompt 定义了风险评级规则但代码没接 -- 生产必须接上，否则审核 Agent 是空壳
5. **Token 内存存储**（`week4/auth/token_exchange.py:63` 内存 dict）：进程重启即丢，生产需 Redis/DB 持久化 + 多实例同步
6. **HITL 人工复核**：排产决策不能全自动，Agent 输出建议 + 排序，人确认后才下发 MES -- Agent 是调度助手不是自动调度员
7. **决策可解释性**：审计日志要能回答"为什么 ORD001 排在 ORD002 前面"，供复盘和投诉追溯
8. **无 Checkpointer 无记忆**（`week3/langgraph_agent.py:558` 教训）：跨轮调度需记忆上次排产结果，避免重复决策/冲突排产

## 跨环节共性问题

1. **幻觉与工具校验**：所有环节 Agent 都可能编造数据（订单号/库存/设备状态）。统一对策：System Prompt 安全规则 + 工具返回值校验 + 不允许 LLM 自补数据。源码锚点：`week1/day3_system_prompt.py:46-55`。

2. **数据不准与新鲜度**：库存账实不符、设备状态延迟、客户等级过期。统一对策：每条数据带时间戳 + 新鲜度校验 + 异常降权，决策前校验数据源可信度。

3. **确定性计算不交给 LLM**：耗料公式、截面积、坏件口径、赔付比例 -- 涉及钱和物料的确定性计算必须调算法/规则，LLM 只做决策和自然语言交互。

4. **多 Agent 协调成本**：环节 6 的 Supervisor 模式有路由+聚合开销，环节 1-5 多数用单 Agent 即可。决策标准：能力是否需要职责分离 + 扩展性需求。

5. **鉴权与审计贯穿**：合同隐私（环节5）、订单修改权（环节6）、设备操作权（环节3/4）都需 Token Exchange + RBAC + 审计。Agent 系统的权限不是可选项。

6. **HITL 人工复核**：接单确认（环节1）、排产确认（环节6）、坏件登记（环节4）-- 涉及钱和生产的决策必须人确认，Agent 是助手不是决策者。

7. **评估闭环**：检索质量（RAGAS）、异常检测（precision/recall）、排产质量（延期率/利用率）-- 每个环节都要有量化评估，不能靠肉眼判断（Week2 教训 → Week4 补 RAGAS）。

8. **业务约束前置**：单材料约束、机型能力矩阵、集群边界、坏件口径、字段映射 -- 这些硬业务规则必须显式编码为约束，不能让 LLM 自由推断。

## 面试讲述策略

1. **讲全景，讲递进**：6 个环节从单能力改造（1-5）到多 Agent 协作（6），对应训练 4 周的递进（手写 ReAct → MCP/LangGraph → Supervisor）。证明不是"会调一个框架"，而是"对制造业智能改造有系统架构思考"。

2. **讲理论，更讲线上坑**：每个环节不只讲"用什么技术"，更讲"线上会出什么问题"。面试官最怕"纸上谈兵"，线上问题（账实不符、API 不稳、幻觉编造、字段映射、坏件口径）证明你懂生产。

3. **讲业务约束，讲诚实边界**：单材料约束、耗料公式不交给 LLM、坏件口径 -- 这些真实业务知识体现"我真的在 3D 打印行业做过"。同时诚实：agent-training 是训练载体，不是公司生产落地，面试讲"这是我对智能改造的系统思考和可行性验证"。

4. **讲安全纵深，讲新课题**：Token Exchange + RBAC + 审计是 Agent 系统区别于普通后端的安全新课题。环节 6 的"审核 Agent 看客户不能改订单、生产 Agent 查库存不能看信用"是权限收缩的具体落地，多数候选人没想过。

5. **讲 HITL，讲边界**：Agent 是调度助手不是自动调度员，接单/排产/坏件登记都要人确认。这条体现工程成熟度 -- 知道 Agent 能做什么、不能做什么。

6. **讲评估闭环**：从 Week2"肉眼判断"到 Week4"RAGAS 量化 + Rubric 后验"，每个环节都要有评估。这条体现"不靠感觉，靠数据"的工程观。

**主动引导方向**：
- 制造业 6 环节智能改造全景（有业务载体 + 有源码 + 有线上坑）-- 差异化优势
- Agent 工程化全链路（原语 → 框架 → 多 Agent → 安全 → 评估）-- 4 周实战
- 真实业务约束（单材料/耗料公式/坏件口径/字段映射）-- 证明行业纵深

**回避**：大模型微调/训练（应用层）、K8s（Docker 够用）、Agent 全自动决策（坚持 HITL）。
