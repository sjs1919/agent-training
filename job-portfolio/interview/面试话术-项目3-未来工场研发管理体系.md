## 一、管理背景

**公司**：未来工场科技，3D 打印服务行业，A 轮→业务成熟，约 300 人。

**岗位**：研发总监（2022.04 空降），管理 6 职能团队：产品 / Java / 测试 / 大数据 / 运维 / 前端。

**空降背景**：公司业务从初创走向规模化，研发需要从"功能堆叠"升级为"体系化交付"。我空降时团队已有一定规模，但没有成体系的研发流程、绩效机制和人才梯队。

**空降时研发真实痛点（摸底洞察）**：
- **没人懂项目管理**：重要需求延期 2 个月，业务部门投诉才知道
- **职场两极分化**：有人上班睡觉，有人加班到吐，领导半夜跟着救火
- **生产系统不稳**：每周必有救火，靠人肉盯，异常定位靠经验

**核心命题**：空降管理者怎么在 6 职能团队上建立信任，然后把研发从"人盯人"变成"体系驱动"？

**管理哲学**：**先稳后建，用体系代替人治。** 空降第一件事不是动结构，是摸底稳团队；体系不是一步到位，是节奏推进——**稳团队 → 成熟期模型嵌套 → AI 转型期**。

**核心设计逻辑：让制度自己长出来，而不是一次设计到位。** 每个模型是上一个模型的"下一站"——数据够了就自然长出下一个制度，新制度又反过来强化旧制度：

```
双周迭代产生任务数据
   │
   ├─→ 识别大/跨组任务 ──→ 催生 项目负责人制度
   │                              │
   │                              └─→ 绩效模型增加"项目负责人激励"维度
   │
   ├─→ 测试纳入，产出质量数据 ──→ 绩效模型增加"质量考核"维度
   │
   └─→ 绩效跑半年，人的数据丰满 ──→ 催生 人才盘点（价值观+绩效双维度）
                                          │
                                          └─→ 识别骨干 → 送做项目负责人
                                                  │
                                                  └─→ 正向反馈：人成长 + 项目顺畅落地
```

> 面试时讲这个逻辑，比罗列"我建了哪些制度"有说服力 10 倍——它说明你不是在搬模板，而是根据数据信号做制度决策。

**立身之本**：靠"身先士卒救火 → 稳住生产 → 改造升级"赢信任——空降后投入智能系统救火，定位异常、稳住生产系统，再了解业务和已实现功能，给出改造方案快速迭代替换，从"每周必有救火"到"正常上下班"，把救火系统逐步改造成核心系统。这是我在公司的立身之本。

### 第一段 — 稳团队（约 3~6 个月）

**为什么先稳**：空降管理者最大的风险是"新人动旧团队"引发反弹。我先不碰结构，用 3~6 个月摸底、倾听、访谈、洞察。

**摸底发现（真实痛点）**：
- **没人懂项目管理**：重要需求延期 2 个月，业务部门投诉才知道
- **职场两极分化**：有人上班睡觉，有人加班到吐，领导半夜跟着救火
- **生产系统不稳**：每周必有救火，靠人肉盯

**关键动作——给团队调整方案 + 身先士卒**：
- **给团队调整方案**：3~6 个月摸排后，聚焦关键问题人员，通过工作安排、业务培训、频繁跟进验证，确认价值观背离、能力无法提升后劝退——让团队知道边界
- **身先士卒救火**：空降后投入智能系统救火，定位异常、稳住生产系统，再了解业务和已实现功能，给出改造方案快速迭代替换——从"每周必有救火"到"正常上下班"
- **外科手术式建制度**：先构建简单的项目负责人制度，再逐步扩展，不动无关结构

**产出**：
- 一份团队与业务瓶颈的摸底结论（后续建流程、建模型的依据）
- **立身之本**：把救火系统逐步改造成核心系统，在团队里站住脚、赢信任

**关键洞察**：稳团队不是"都不得罪"，而是"让对的人留下、让不匹配的人离开 + 用实事证明你能扛事"。

### 第二段 — 成熟期（模型嵌套 · 让制度自己长出来）

**目标**：不靠一次设计到位，而是让体系**涟漪式扩散 + 模型自生长**。

**扩散路径（从开发组单点突破 → 涟漪式扩张）**：

```
开发组双周迭代（建流程后半段启动，约3月基础设施 + 3月运转）
   │ 3月后 → 产品团队纳入（向前2周锚点）
   │ 6月后 → 测试团队纳入（产品跑3月后）
   │ → 绩效模型数据积累 → V1→V4 迭代
   │ → 业务对齐：月度目标+业务研发双周例会 → 黑盒变透明
   │ → 人才盘点：价值观+绩效双维度 → 识别骨干
   │ → 项目负责人制度：人才培养器
   │ → 人的产出：4 主管 + 3 骨干 + 1 连续晋升
```

**核心设计逻辑「让制度自己长出来」**（已在管理背景）——双周迭代产生任务数据 → 识别大/跨组任务催生项目负责人制度 → 绩效模型增加对应维度；测试纳入产出质量数据 → 绩效模型增加质量维度；绩效跑半年人的数据丰满 → 催生人才盘点 → 识别骨干送做项目负责人 → 正向反馈：人成长 + 项目顺畅落地。

**人的结果（真实案例）**：
- 老员工 OMS 骨干：教练式辅导 → 晋升主管
- 招来产品主管：背景好，项目倾斜 + 跨部门影响力搭建 → 晋升
- 招来 Java 主管：原主管离职备份顶上，教练辅导 + 共建智能机器系统 → 晋升
- 招来测试主管：专业强但情绪弱，~1 年贴身陪跑，情绪关卡 + 标杆分享 → 晋升
- 3 骨干（OMS/前端/Java）：绩效绩优 → 人才盘点 → 晋升，1 人连续晋升

**人才盘点机制**：
- 四象限（参照九宫格），专业技能 + 价值观双维度
- 你 + HRBP 共同牵头
- 绩效模型指标挂钩，留足主管主观评价空间
- 每季度盘点 + 更新培训计划
- 每年 1 次职级职等晋升 + 年度人才复盘

- **AI 转型方式**：**愿者上钩**——走鼓励、引导、吸引的模式，不是强制推

#### workspace 团队提示词（工程化协作规范）

我落地的不只是"会用某个 AI 工具"，而是一整套**工程化协作规范**，让团队有统一的 AI 协作方式：

**① 项目规范文件（CLAUDE.md / AGENTS.md）**——项目级"团队提示词"
- 每个项目根目录建 `CLAUDE.md`（或 AGENTS.md），把**技术栈、代码规范、架构约定、禁止事项、常用命令**写进去
- 效果：AI 每次启动自动加载这些约定，团队成员不用重复口头交代
- 培训材料讲的一句话：「重复不断的规则，可以提取成为原则，加入 AI 工具规范里」

**② 按领域拆分的编码规则（.trae/rules/）**——给 AI 的"边界"
- 按模块拆分：架构 / 错误处理 / 日志 / 数据库 / Redis / API / 前后端对接 / 测试 / 运维（token-hub 实际落地 10 个规则文件）
- 效果：碰什么模块加载对应规则，AI 不会越界乱写
- 例：错误处理红线「严禁打日志然后丢弃，所有 error 必须向上传播」

**③ 双仓分离（代码仓 + 文档仓）**——AI 协作的"记忆库"
- 规格（spec）、计划（plan）、任务（todo）统一放文档仓，代码仓只放代码和编码规范
- 效果：需求来源可追溯，AI 干完活能回到源头核对，不会凭感觉

#### AI 代码门禁（质量底线）

我建立了一套**强制验收门禁**，AI 写的代码也必须过。关键是：**四门禁本来是约束人的研发流程，我把 AI 写代码也纳入同一套验收标准——人机同一标准，不是另起炉灶。**

**工作流四门禁**（spec → plan → todo → 四门禁全流程）：
```
需求澄清 → 任务拆分 → 9角色评估 → 计划验证 → 用户确认 → 执行自验 → 代码验收 → CR走读 → 部署
  待确认     待确认      🔴门禁       🔴门禁1       人工       每任务核对   🔴门禁2   🔴门禁3   🔴门禁4
```

- **门禁1 计划验证**：计划写完打开 spec 逐条核对，spec 每条验收标准在计划中都有对应任务，遗漏任何一条禁止进入下一步
- **每任务核对**：每个任务完成后打开 spec 逐条读验收标准 + 跑测试 + 编译，通过才能做下一个
- **门禁2 代码验收**：用 CodeGraph 读改动代码，逐项对照计划任务，全量测试 + 端到端验证
- **门禁3 CR 批判式走读**：以批判者视角逐行审阅（有没有 bug？边界条件？错误处理？），发现问题修复后重新走读，**不通过禁止提交/合并/部署**
- **门禁4 部署审批**：无文档禁止部署，先写文档 → 用户审核签字 → 执行

- **6 场 AI 转型培训**：

  - 其余 4 场小组内部培训（Prompt 工程 + AI 编程实战）

## 三、关键机制详解

> 面试官追问某一机制时，从这里取弹药。三个机制是三件不同的"工具"，别混着讲。

### 3.1 双周迭代 = 节拍器（保证节奏）

**一句话**：产品/研发/测试错位 1 周的三岗流水线，7 个管理工具环环相扣。

**为什么有效**：错位设计避免"需求来了研发没空、研发做完了测试没准备好"的串联等待；固定 2 周时间盒让团队有稳定输出节奏。

**数字支撑**：负载率稳定在 70%~90% 区间，工时计算规则精确（1 人天 = 7 工时）。

### 3.2 绩效模型 = 指挥棒（引导方向）

**一句话**：交付 60% + 质量 20% + 技术沉淀 15% + 其他 5%，17 个月迭代 4 版。

**为什么有效**：权重骨架稳定（体现设计者信心），细则持续迭代（PDCA 闭环）；管理即考核，所有指标有数据源，争议大幅减少。

**数字支撑**：质量基线内化，Bug 三项指标多数人满分；分数区分度稳定 70~80 分区间。

### 3.3 项目负责人权责机制 = 人才培养器（梯队造血）

**一句话**：积分制奖惩 + 新手保护期 + 人才池轮换 + 反讲培养，把"培养项目负责人"从口号变成制度。

**为什么有效**：干得多有激励、延期了有责任；新手有保护期敢接活；人才池轮换保证梯队流动。

**数字支撑**：1-3 分弹性积分、前 2 项目保护期、反讲全员参与。

### 3.4 人才盘点机制 = 组织雷达（识别骨干）

**一句话**：四象限（参照九宫格），专业技能 + 价值观双维度，你 + HRBP 共同牵头，每季度盘点 + 每年 1 次职级职等晋升。

**为什么有效**：绩效模型跑半年人的数据丰满后自然催生人才盘点；绩效指标挂钩 + 留足主管主观评价空间，避免"纯绩效分高就是人才"的机械判断。

**数字支撑**：识别出 4 主管 + 3 骨干 + 1 连续晋升；价值观 + 绩效双维度。

### 3.5 AI 转型三件套 = 团队升级引擎（AI 转型期）

**一句话**：workspace 团队提示词 + AI 代码门禁 + 用结果说话——不硬凑大厂 Guild/DemoDay 套路，诚实讲这三件事。

**为什么有效**：workspace 提示词让团队共享协作规范（不是个人黑箱）；AI 代码门禁守住质量底线（AI 写的代码也要过验收）；用结果说话（lexy 商城生产交付）证明不是"玩票"。

**数字支撑**：lexy 商城 2026.06 部署生产、俄罗斯市场开售（待项目4 稿补指标）；6 场培训，其中 2 场公司级覆盖 200 余人（大模型能做什么 + AI coding 怎么做）+ 4 场小组内部培训（Prompt 工程 + AI 编程实战）。

## 四、管理亮点

### 4.1 空降整合的推进节奏（最有说服力）

3~6 个月稳团队（摸底→调整方案→身先士卒救火）→ 成熟期模型嵌套（开发组单点→涟漪扩散到产品/测试，体系自生长）→ AI 转型期（个人探索→团队交付）。先稳后建，用体系代替人治，不靠空降者的"官威"推事。

### 4.2 数据驱动的绩效体系（管理即考核）

所有绩效指标有明确数据源，主管不拍脑袋；开发可自查负载率、延期记录、Bug 修复时效，争议大幅减少。从 L1 规则驱动 → L2 机制驱动 → L3 文化驱动，17 个月迭代 4 版。

### 4.3 双周迭代 7 工具闭环

需求收集 → 禅道录入 → 任务分配 → 负载盘点 → 测试跟踪 → 线上问题 → 工时评估，7 个工具环环相扣，形成"日常管理 → 绩效考核"完整数据链路闭环。

### 4.4 人才培养制度化（梯队造血）

项目负责人权责机制把人才培养变成制度：新手保护期、人才池轮换、反讲培养、绩效数据公开。团队从"要我做"变成"我要做"。

### 4.5 从 0 到 1 建 14 方向研发流程

研发流程 v1.0→v2.0、敏捷融合 DevOps、版本分支管理、测试环境管理、项目复盘体系、离职交接规范、新员工培训，覆盖研发全生命周期。

### 4.6 交付改善（最有说服力的一条）

空降时是"人盯人救火"：没人懂项目管理、重要需求延期 2 个月业务投诉才知道、每周必有救火。走的时候是"体系驱动"：正常上下班、质量基线内化、Bug 三项指标多数人满分。

**改善动作**：身先士卒救火（定位异常、稳住生产）→ 给改造方案快速迭代替换 → 建流程（双周迭代）→ 建绩效模型（质量内化）。救火系统逐步改造成核心系统，成为立身之本。

> 一句话卖点（两版，按岗位选）：
> - **管理岗**：空降 4 年，把救火团队带成体系驱动。
> - **AI 岗**：用工程化方法约束 AI 协作，带团队交付生产级 AI 系统。

### 4.7 AI 转型的带头作用（第三段最有说服力）

作为研发总监躬身验证 AI 全链路（个人探索→token-hub→lexy→单 Agent→排程排产），蹚明路径后以"鼓励不强推"方式带团队，用 workspace 提示词 + AI 代码门禁 + 结果说话，组织 6 场 AI 转型培训，完成 lexy 商城（AI 驱动生产交付）+ 排产助手（Agent 团队级验证）。

> 与项目 2/4 关系：项目 2 = 你个人的 Agent 技术晋级线；项目 4 = AI 转型期的团队交付产物；项目 3 只讲"你作为管理者怎么带团队走进 AI"，具体技术细节由项目 2/4 承接。

## 五、难点与权衡

### 5.1 空降信任建立难

空降管理者最怕"新人动旧团队"引发反弹，6 职能团队各有既有习惯和利益格局。

**解法**：先摸底 1 个月，不急于动结构；先倾听再判断；用专业能力 + 把事做成建立信任；先稳后建。

### 5.2 制度落地阻力大

新流程、新绩效机制推行初期，团队普遍抵触（"又搞形式主义""绩效就是扣钱"）。

**解法**：管理即考核——绩效分数不是主管拍脑袋，而是从日常工具自动提取，可追溯、可自查；数据公开透明，让团队看到"公平"；先试点后推广，用结果说话。

### 5.3 纯量化被"刷分"

V1 固定 +2 分导致"刷文档"现象，有人写大量低质量文档刷分。

**解法**：V2 引入弹性封顶（+2 降为 +1、3 分封顶），从"数量导向"转为"质量导向"。

### 5.4 量化指标的盲区

纯量化考核不到"过程质量"和"创新探索"，容易被"优化"。

**解法**：V4 引入主管主观判断权（月度测试质量 ±5 分、CodeView -3~3 分）+ 探索型任务，从"只看产出"到"过程 + 结果并重"。

### 5.5 汰换与稳定的平衡

空降半年"优化"团队，是敏感话题。绩效汰换可能引发团队恐慌。

**解法**：汰换依据是长期绩效数据（非主观好恶）+ 无改进意愿；汰换不是目的，是"让团队知道边界 + 激活人才池"的手段；用绩效数据公开支撑决策，减少争议。

## 八、口径红线

- **「劝退」表述要诚实 + 有依据**：劝退基于「价值观背离 + 能力无法提升」且经过「工作安排、业务培训、频繁跟进」验证，不是主观裁人；面试官若质疑"空降就动人"，回应"先摸底 3~6 个月有依据，且同时身先士卒救火证明不是只会开人"
- **救火叙事别自曝系统脆弱**：讲"身先士卒救火→改造成核心系统"是亮点（你能扛事、懂业务），但别渲染"前任团队多无能"，聚焦"我接手后怎么稳住的"
- **AI 转型期口径（已确认）**：愿者上钩——鼓励、引导、吸引，不强迫；愿意的给工具/规范/培训/项目机会，不愿意的尊重选择；用结果说话（lexy 生产交付 + 排产 demo）；不硬凑大厂 Guild/DemoDay 套路；金句「宁可拥抱 AI 被大模型蒸馏，也别被社会淘汰」
- **与项目 1 区分**：项目 1（智能机器管理系统）是技术/业务项目，讲设备管理 700+ 台；项目 3 是管理项目，讲体系搭建——两者别混着讲
- **与项目 2 区分**：项目 2（排产助手）是 Agent 技术项目，讲技术能力；项目 3 只讲"你作为管理者怎么带团队走进 AI"，AI 技术细节由项目 2 承接，不重复

## 十、面试叙事素材（AI 转型期 · 可讲成故事）

> 面试官问「你怎么带团队做 AI」时，从这里取。讲**故事**，不是讲流程清单。
> 核心逻辑：**你不是在推 AI 工具，是在用工程化方法约束 AI 协作，且交付了生产系统。**

### 叙事主线（2 分钟版）

> 2025 年底我开始个人探索 AI 编程，从 Cursor 到 Claude Code。我很快意识到一件事——AI 编程真正的瓶颈不是"用哪个工具"，而是**怎么让 AI 稳定地产出符合规范、能合入生产的代码**。所以我做的第一件事，不是推工具，而是定规范。
>
> 我给团队落地了一套「工程化约束 AI」的体系：每个项目建 CLAUDE.md 项目规范文件，把技术栈、代码规范、禁止事项写进去，AI 每次启动自动加载；再按领域拆成编码规则（架构/错误处理/日志/数据库），碰什么模块加载什么规则，AI 不会越界乱写。
>
> 同时我定了四道强制验收门禁：计划验证、代码验收、CR 批判式走读、部署审批。AI 写的代码一样要过门禁，不通过禁止提交。
>
> 推广上我走「愿者上钩」：鼓励、引导、吸引，不强迫。愿意的人我给工具、给规范、给培训、给项目机会；不愿意的人我尊重选择。我组织 6 场培训把"AI 能做什么、怎么做"讲清楚——2 场公司级科普覆盖 200 余人，其余是小组内部的 Prompt 工程 + AI 编程实战。
>
> 用这套方法，我团队实际交付了两个生产项目：**lexy 商城**（AI 驱动全流程生产交付，2026 年 6 月部署生产、俄罗斯市场开售），和**排产助手**（3D 打印 / CNC 排程排产 demo，Agent 团队级验证）。团队从"我会用 AI 工具"升级到"用工程化方法约束 AI 协作"。
>
> 我常跟团队说一句话：「宁可拥抱 AI 被大模型蒸馏，也别被社会淘汰。」

### 三个可展开的故事点（面试官追问时）

**故事点 1：为什么是"工程化"而不是"用工具"？**
- 背景：2025 年底团队已经在用元宝/千问/豆包做简单代码生成，但产出参差、没人敢合入生产
- 洞察：AI 的产出质量取决于「给它的上下文 + 边界」——上下文靠 CLAUDE.md 项目规范，边界靠编码规则 + 验收门禁
- 行动：建立 CLAUDE.md + .trae/rules/ + 四门禁
- 结果：lexy 商城（生产交付）、排产助手（团队级验证）

**故事点 2：AI 代码门禁怎么保证质量？**
- 背景：AI 能生成代码，但"能跑"≠"该合入"
- 行动：四道门禁——①计划验证（spec 每条验收标准在计划中有对应任务）②代码验收（CodeGraph 读代码对照 plan + 全量测试）③CR 批判式走读（逐行找 bug，发现问题修复后重新走读）④部署审批（无文档禁止部署）
- 洞察：门禁对 AI 和人一视同仁，AI 写的东西也要能回答"这行代码有没有 bug？边界条件覆盖了吗？"
- 结果：AI 产出进入生产链路，质量可控

**故事点 3：workspace 提示词具体是什么？**
- CLAUDE.md（项目规范）：技术栈 / 代码规范 / 架构约定 / 禁止事项 / 常用命令
- .trae/rules/（领域规则）：架构 / 错误 / 日志 / 数据库 / Redis / API / 测试 / 运维，碰什么模块加载什么
- 双仓分离（代码仓 + 文档仓）：spec/plan/todo 放文档仓，需求来源可追溯
- 培训：2 期 Prompt 工程培训（5 条铁律 + 4 种模式 + 参数化模板），让团队人人会用
