## 一、开场总览（P0 · 必考）

### Q1. 你 4 个项目分别解决什么问题？怎么递进的？
> 一句话锚定：技术线 1→4→2 递进，管理线项目3 贯穿。

**回答**：
> 我在未来工场 4 年做了一条技术线、一条管理线。
>
> **技术线**三个项目：项目1 智能机器管理系统是**技术根基**——6 服务流水线管 700+ 台设备，把"凌晨人工盯电话"变成"7×24 无人值守"，新品牌接入从 1 个月缩到 1 周。项目4 lexy 商城是**AI 生产交付**——用 AI 驱动全流程，3 周交付传统要 1.5 人月的商城。项目2 排产助手是 **Agent 技术晋级**——从单 Agent 一路做到多 Agent 编排，验证制造业调度场景。

## 二、项目1 智能机器管理系统（P0 基础 + P1 深挖）

### Q3. 项目1 简单介绍？（P0）
**回答**：统一管理多品牌、多类型生产设备的智能调度与执行系统。设备从不足 100 台扩展到 700+ 台（3D 打印/尼龙/金属/CNC 四类），7+ 品牌 API 统一适配。架构是 6 服务流水线（下载→解析→校验→转换→上机→上报）+ 策略/适配器模式，实现"USB 式热插拔"接入新品牌——对接周期从 1 个月缩到 1 周。

### Q4. "USB 式热插拔"具体怎么实现？（P1）
**回答**：核心是适配器模式。每个品牌厂商有独立 API，我们定义统一接口，新品牌只需写一个适配器实现接口，注册进系统即可——不改业务逻辑。策略模式处理不同品牌的差异化逻辑（如参数格式、上报协议）。6 服务流水线负责标准化的下载→解析→校验→转换→上机→上报全流程，品牌差异被封装在适配器层。

### Q5. 单集群到多集群演进？（P1）
**回答**：富海产区设备集中度突破单集群上限，我们建了健康度指标体系预判瓶颈，主动从单集群重构为多集群负载均衡。**核心不是"扩容"，是"先用指标预判，再主动重构"**——不是等到挂了才动。

### Q6. 和项目2 的关系？（P0）
**回答**：项目1 是**设备管理层**（6 服务流水线管设备），项目2 排产助手是**决策层**（Agent 做排程排产）。项目1 的 MES 排程演进路线里规划引入 Agent 智能调度，项目2 正好承接验证。

## 三、项目2 企业级 Agent 排产助手（★重点 · 最详细）

> 面试官最可能深挖的项目——技术深度最深。分五组：**晋级线 / 架构 / RAG / 安全权限 / 评估与差距**。

### 3.1 Agent 晋级线（P0 · 回应"真懂还是贴标签"）

#### Q7. 你的 Agent 是怎么一步步学起来的？（P0）
**回答**：不是一步到位，有一条晋级线——先是企微知识库里的**机器故障查询**（单 Agent 最小闭环，理解"一个 Agent 调一个知识库"）；再**自建单 Agent**装多工具（知识库 + 订单打印 + 机器状态 + BPC 转换 + 故障预警），学会多工具调用；最后才做**排程排产**这种需要 Agent 编排 + 多 Agent 协作的复杂度。前期还用 Java 建了 MCP Server 做工程化底座。每一步都有实物，不是培训班出来贴标签。

#### Q8. 先手写 ReAct 再换 LangGraph，区别是什么？（P1 · 小明最关注）
**回答**：我 week1 手写 ReAct 循环，week3 换 LangGraph。手写的价值是**理解原语**——循环怎么转、工具结果怎么注入、什么时候该停；换框架后能看清**框架替我做了什么**（状态管理、条件边、checkpoint）。这让我 debug 时不懵：知道框架背后是那个循环。

### 3.2 架构设计（P0 · 老张最关注）

#### Q9. 项目2 整体架构？（P0）
**回答**：LangGraph 状态图 + Supervisor 多 Agent + 权限治理三层。编排层用 LangGraph 状态机驱动 Agent 循环（分析→选工具→执行→评估→生成）；权限层是 STS Token Exchange + RBAC + 审计的洋葱型三道防线；观测层是 OTel 同构的 Tracer，可插拔 backend。工具层用 ToolRegistry 注册中心，RAG 层做混合检索。

#### Q10. 单 Agent 和多 Agent 怎么选？（P1）
**回答**：按问题复杂度切换。简单快答走单 Agent（快、省 token），复杂问题走多 Agent Supervisor 分派专业子 Agent（reviewer 订单评审 / scheduler 生产评估）。共享工具层、RAG、鉴权——一套代码双模式。

#### Q11. LangGraph 状态图的核心节点？（P1）
**回答**：analyze_intent（意图识别）→ select_and_execute（LLM 决策调哪些工具→执行→注入结果）→ evaluate_results（评估结果够不够）→ should_continue 条件边（末条是 tool 结果就继续循环，是 assistant 文本就出答案）→ generate_answer（过 guardrails 输出护栏）。**安全阀：迭代 ≥5 轮强制结束**，防死循环。

#### Q12. 状态持久化怎么做？（P1）
**回答**：LangGraph SqliteSaver checkpointer，`--chat --thread` 跨进程恢复会话。从 checkpoint 显式取历史，保持 dict 消息格式（避免 add_messages 转对象风险）。进程重启后多轮对话能续接。

#### Q13. 上下文压缩？（P1）
**回答**：summarization buffer——保留 system + 最近 6 条，中间用 LLM 摘要替代。控长对话 token 成本，避免上下文无限膨胀。

### 3.3 RAG 混合检索（P0 · 必考）

#### Q14. 为什么不用纯向量 RAG？（P0）
**回答**：中文 MiniLM 向量召回弱，top1 常召回错误文档（比如问合同条款，召回的是历史延期记录）。所以加 BM25 补**字面命中**——"广州航天"这种专有名词必须精确命中——再 RRF 融合两路排名，最后 Cross-Encoder 精排。目标合同 top1，rerank 分 >0.9。

#### Q15. RRF 融合怎么算？（P1）
**回答**：Reciprocal Rank Fusion，两路排名各算 `1/(k+rank)`（k=60），累加得分，取融合后 topN 送重排。

#### Q16. 重排器用的什么？（P1）
**回答**：BAAI/bge-reranker-base，精排 top3，目标合同 rerank 分 >0.9 才返回。重排比向量/BM25 都准，因为是 cross-attention 双文档建模。

#### Q17. 合同条款检索比纯向量准的例子？（P1）
**回答**：合同里有特殊条款（广州航天、赔付规则）。纯向量问"航天件的赔付规则"可能召回别的合同；BM25 先字面命中"航天"相关合同，RRF 融合后重排，把"赔付规则"那段精确捞出来。制造业的专有名词多，纯向量中文场景会翻车。

### 3.4 安全与权限（P1 · 老张会深挖）

#### Q18. 洋葱型三道防线是什么？（P1）
**回答**：第 1 层网关/运行时鉴权；第 2 层 STS Token Exchange（父令牌→受限子令牌）；第 3 层工具层 RBAC 强制（无权拒绝 + 审计 JSONL 落盘）。层层收口，单点失守不至于全盘失守。

#### Q19. Token Exchange 怎么防提权？（P1）
**回答**：STS 签发用户令牌后，交换出受限子令牌给子 Agent（reviewer/scheduler）。**子令牌权限 ≤ 父令牌**，交换时校验收缩，5min TTL 过期。子 Agent 拿受限令牌调工具，没法越权到父级权限。

#### Q20. RBAC 在哪一层强制？（P1）
**回答**：工具层（洋葱第 3 层）。每次工具调用经 guard.py 校验权限，无权直接拒绝 + 写审计。不是只在前端/路由拦，而是**执行入口强制**，绕不过去。

#### Q21. guardrails 拦过什么？（P1 · 老张追问）
**回答**：输出护栏检测越权指令和敏感信息，block/warn/off 三档。缺段落检查防"AI 没查到就编"。**具体样例**：问合同赔付但模型想调用全量工具时，权限层拦下；输出含敏感字段时护栏拦截。（若被追问更深，诚实讲：guardrails 在 R2 补的，效果数据还没做专门统计。）

### 3.5 评估、成本与差距（P0 · 决定成败）

#### Q22. 你的 Agent 怎么评估的？（P0 · 陷阱题）
**回答**：10 组排产场景 ground truth + 加权指标（工具调用准确率 F1 0.3 + 回答完整性 0.5 + 订单命中 0.2）+ runner 跑批，单 case 综合分 ≥0.6 通过，汇总 ≥7/10 过回归基线。
> ⚠️ **陷阱**：别主动说 RAGAS。被追问「RAGAS 在哪」→「week4 训练脚本里跑过，demo 用自研指标更可控，因为工具调用这种场景自研指标更能对准业务目标。」

#### Q23. 两级缓存区别？（P1）
**回答**：L1 精确缓存 SQLite——相同 prompt 命中 <1ms、0 token；L2 语义缓存 Chroma cosine——近义问题改写命中 ~50ms（阈值 0.20 校准）。L2 命中就跳过整图执行。加上 CostTracker 自动计费 + 预算熔断，控 Agent 多轮调用的 token 成本。

#### Q24. 观测层怎么接 Jaeger？（P1）
**回答**：自研轻量 Tracer（Span + trace_id），OTel 同构接口 + 可插拔 backend。`OTEL_EXPORTER=otel` 就发 OTLP 到 Jaeger 4317，换 backend 不动业务代码。曾踩坑：span 结束后才写 token 属性会丢，改成延迟批量导出（整轮 query 结束才 flush）。

#### Q25. 生产级差距在哪？（P0 · 决定诚实的分量）
**回答**：这是**教学版验证**，生产化差距我列过表：缺 JWT 签名/refresh token（权限）、采样/异步导出（观测）、增量索引/多租户 RAG、NL2SQL、CI 集成轨迹评估；单 Agent 模式 token=None 可绕过鉴权（缺 FORCE_AUTH 开关）。**我主动列差距，因为知道"验证了什么、还没到生产"比假装生产更可信**。生产化路径：接真实业务库 + 规则引擎 → Agent 调度。

#### Q26. 工具安全怎么做？（P1）
**回答**：ToolRegistry 参数白名单（只传 Schema 定义字段，防 LLM 把 comment 带进 WHERE）+ RBAC 强制 + 沙箱（R1：超时控制 + 指数退避重试 1s→2s→4s）+ tracer 自动埋点。MCP 是工具协议化演进方向，本地 fast path + MCP 子进程双模式。

#### Q27. 项目2 为什么是"团队级验证"不是生产？（P0 · 口径）
**回答**：因为它验证的是**工程化方法论**——权限/观测/评估/护栏这些生产级关注点，不是部署规模。业务数据是 CSV 模拟（不是真实业务库），所以是"团队级验证可行性"，不是规模化生产。这跟 lexy（真上线）不同——lexy 是生产交付，排产是方法论验证。

## 四、项目3 研发管理体系（P0 管理面）

### Q28. 空降你怎么做的？（P0）
**回答**：三段式。第一段 3~6 个月稳团队——摸底倾听，找最大公共痛点，给团队调整方案，同时身先士卒救火稳住生产，把救火系统改造成核心系统（立身之本）。第二段成熟期让制度自己长出来——开发组双周迭代单点突破，涟漪式扩散到产品/测试，绩效模型从数据里长出来迭代 4 版，带出 4 主管 3 骨干。第三段 AI 转型期——先躬身验证 AI 全链路，再以愿者上钩方式带团队。

### Q29. "让制度自己长出来"是什么意思？（P1）
**回答**：不一次设计到位，而是让体系随数据涟漪式扩散。双周迭代产生任务数据→识别大/跨组任务催生项目负责人制度；测试纳入产出质量数据→绩效模型加质量维度；绩效跑半年人的数据丰满→催生人才盘点→识别骨干送做项目负责人→正向反馈。**每个模型是上一个的下一站**，不是搬模板。

### Q30. 绩效模型 4 版演进？（P1）
**回答**：交付 60% + 质量 20% + 技术沉淀 15% + 其他 5%，17 个月迭代 4 版，从 L1 规则驱动→L2 机制驱动→L3 文化驱动。V1 全量化；V2 发现被刷分引入弹性封顶；V4 补纯量化盲区（主管主观判断权 + 探索型任务）。核心是**管理即考核**——所有指标有明确数据源，主管不拍脑袋。

### Q31. 项目3 和项目2/4 什么关系？（P0）
**回答**：项目3 是**管理线**（管理者视角带团队），项目2/4 是**技术结果**。项目3 的 AI 转型期讲"我作为研发总监怎么带团队走进 AI"，lexy（项目4）和排产（项目2）是"用结果说话"的结果例证。**讲项目3 不展开技术细节，技术细节由项目2/4 承接。**

### Q32. 团队有人抵触 AI 吗？（P0）
**回答**：我走「愿者上钩」——鼓励、引导、吸引，不强迫。愿意的人给工具/规范/培训/项目机会（lexy、排产都是愿意的人做出来的）；不愿意的尊重选择。做了 2 场公司级科普（200 余人）+ 4 场小组培训，让先行者做出成果自然吸引后来者。金句：「宁可拥抱 AI 被大模型蒸馏，也别被社会淘汰。」

## 五、项目4 lexy 商城（P0 商业面）

### Q33. 项目4 简单介绍？（P0）
**回答**：AI 驱动全流程生产交付的跨境电商商城，3 周交付传统要 1.5 人月的系统。前端 Figma→大模型微调→界面交付；后端用户故事→规格→计划→TDD 先写测试→AI 按测试编码→自动化验收→人工轻量验收→上线。2026.06 部署生产、俄罗斯市场开售。

### Q34. 3 周怎么做到的？（P0）
**回答**：第 1 周搭框架/需求调研/组织用户故事打地基（没进研发），第 2-3 周 AI 编码 + 自动化验收。关键是规格驱动 + TDD——测试先写好（可执行的规格），AI 按测试编码目标明确不漫游；同一套测试做自动化验收，人工只做简单功能测试，**测试强度比传统轻 50% 以上**。

### Q35. 你的角色是什么？（P0）
**回答**：全程参与——需求调研、组织用户故事、构建前后端框架、联调交互、admin 端全栈实现；主导工具/模型/套餐选型、三端交互、敏感信息保护、AI 代码门禁、全自动化测试验收策略。**既是技术管理者（定方向/门禁/策略），又亲手写代码。**

### Q36. GMV 多少？（P0 · 陷阱题）
**回答**：诚实讲——新系统、新市场、起步期，有零星用户访问和订单。**我不编数字**。这个项目真正的数字是交付效率（3 周 vs 1.5 人月）和工程化方法（TDD + AI 自动化验收），不是起步期的 GMV。

### Q37. 和项目2 的区别？（P0）
**回答**：排产是 **Agent 技术晋级**（技术深度，验证方法论）；lexy 是 **AI 生产交付**（全流程验证，真上线）。一个证明我能把 Agent 做到深处，一个证明 AI 能交付生产级系统。

## 六、跨项目 / 综合题（P0 · 决定岗位匹配）

### Q38. 你是技术管理者，为什么亲手写代码？（P0 · 老张/小明最关心）
**回答**：研发总监不该是"只会开会的人"。lexy 我亲手做 admin 全栈，排产我手写 ReAct 再换框架——**懂技术才能定门禁、审架构、被团队说服**。我定规则（CLAUDE.md/编码规则/四门禁），但要亲手验证规则可行，才敢让团队照做。

### Q39. 你最大的失败/教训？（P1）
**回答**：讲一个真实的——api-client 跳过 api-spec 对照，导致 10+ 页面接口路径字段全不一致，登录失败、列表全空。**教训：AI 协作必须强制 API 契约对齐**，之后建了规则（8 项核对 + httptest）。踩坑→建规，是工程成熟的表现。（备选：计费 BUG 平台亏损 97.7%——缓存双重计费三连，教训是高一致性场景必须并发专项审计。）

### Q40. 你怎么带团队用 AI？（P0 · 老周最关心）
**回答**：三件事——①**定规范**：CLAUDE.md 项目规范 + .trae/rules 编码规则 + 四门禁，AI 在边界内干活；②**给培训**：6 场培训（2 场公司级 200 余人 + 4 场小组）让团队人人会用；③**用结果说话**：lexy 交付生产、排产验证 Agent——让先行者做出成果自然吸引后来者。**我不是推工具，是工程化约束 AI 协作。**
